**The word.** Typing `train <N> [<N> …]` at the surface opens an autonomous, normal-stakes workload with no plan step. Its brief (`trainBrief`, `surface/src/merge-train.ts`) carries the procedure. A surface-only `train:` entry binds the PRs, the way `test-pr` binds them, so the lane runs `lane_full_test` on them without pushing to them. `train <wl-…> <N> …` adds PRs to an open train and relaunches its lane if none is live. The word refuses: a PR already on the train, a PR on another open train of the same repo (unless Jo skipped it there), a workload that is not a train, and a standing or closed workload. A bare `train`, or `train q-…`, still answers an open question that offers the word.

**Land-first checks.** On repositories with the ledger activation `land-first <repo> on`, `lane_full_test` uses the hosted fast PR gate except for schema, dependency/lockfile and production-stakes exceptions, which require a full Mac suite. The full suite then runs on main after landing; red or unknown main holds further landings. See `migration/items/train-land-first.md` for the unchanged strict `as2/full-suite` ruleset, close coverage, recovery, and activation order. When land-first is off, the train retains its existing full-suite-before-merge behavior.

**The procedure.** One PR at a time:
- work out the PR's stakes (`merge-train.ts stakes`). Normal means a same-repo `wl/<id>` branch of a normal-stakes workload **and** a main protected by an active ruleset that requires `as2/full-suite` on an up-to-date head (read from `GET /repos/{o}/{r}/rules/branches/main`, which needs no admin). Anything else is production;
- merge `origin/main` into the PR branch, never rebasing;
- if the merge conflicts, run `merge-train.ts resolve`. It fixes conflicts limited to MIGRATION.md, `migration/items/` and `install/manifest.tsv`, converting the PR's new legacy M7 blocks into item files and taking the union of the manifest rows;
- run the full suite with `lane_full_test`;
- before merging or asking, a readiness check common to both stakes: the head equals the tested sha, the PR is MERGEABLE, and the head contains the fetched main. A moved head re-prepares a fresh worktree at the new head; a moved main goes back to merging main in. Then stakes are checked again. Normal: `gh pr merge --merge --match-head-commit <tested head>`, with no question to Jo. Production: ask Jo merged / skip / stop with the fresh head and run, and move on to the next PR while that question is open;
- a red PR, a conflict outside the auto-fix set, or a stack problem goes back to its owner with `lane_train_return` (below), with no question. A runner error twice at one head, or a merge refused twice, is a lane-written `train-error:` and the PR is passed over until a later pass;
- a `red-main` result (every failure also fails on main's base, judged by the runner) lets the PR merge: the lane finds or files a `main-red` issue on the repo (`gh issue list/create --label main-red`), records `main-red: <url> run <id>`, and merges as for a green.

**Returning a PR to its owner (part 2, D6-D8).**
- `lane_train_return { pr, kind: red|conflict|stack, detail }` (`surface/extensions/lane-tools.ts`) reads the detail file and the PR's current head with `gh pr view`, then writes the train's `train-task: tt-<id> pr <n> attempt <a> kind <k> head <sha> owner <wl-…|none>` with the detail below it (`recordTrainTask`). The owner is D1's: the open workload of a same-repo `wl/<id>` head branch on the train's repo, else `none`. The attempt is 1 plus the PR's failed settles since Jo's last `retry`; after attempt 2 fails the tool refuses, since Jo's alert is due. A PR with an unsettled task is not returned again.
- The owner hears of the task in its first prompt (`ownerTasks` into `firstPrompt`) or, when a lane is live, as an aside once per session (`pushTrainTasks`, `surface/extensions/lane.ts`). It fixes on the head branch, pushes, and runs `lane_full_test`; or records `train-task-failed: <id> <why>` and releases.
- `settleTasks` gives each task one `train-task-settled: <id> fixed|failed <evidence>`: fixed when the first non-error run the owner requested after the task is green (or red-main) at a new head that is still the PR's head; failed on a red, on `train-task-failed:`, on an owner lane exit with no push since the task, or at the mark of the first 2 h stretch with no push (even if a later push came before the tick saw it). A push is one GitHub records: the tick lists the repository activity of the PR's head branch (`gh api repos/<o>/<r>/activity -f ref=refs/heads/<branch> --paginate --slurp`, every page; every entry but a `branch_deletion` (push, force push, a PR merged into the branch, merge queue, creation), each its `after` sha and GitHub's `timestamp`), so the time of a push is GitHub's, not the time the owner asked for a run, and delaying a request moves no deadline. A runner request and a `push-dest:` entry are never pushes. The listing counts only when this pass read it and it names the PR's current head (a head off H0 it does not name means GitHub's record is behind); otherwise neither push rule settles the task this pass, and a green at or after the earliest moment a push rule could have failed it (the 2 h mark of t0, or an owner exit) waits for the listing. A runner error never settles and never counts as an attempt. `red-main` needs each failing test name to fail at least as often on base (a multiset).
- For owner `none`, `openTrainFix` opens one fix workload per (repo, PR), or reuses the open one carrying `train-fix: repo <r> pr <n>`, with the brief, `repo:`, `done:`, a `train-fix: … train-entry <en-…>` binding (valid only while that `train:` entry lists the PR), `push-dest:` at the head branch and `launch-requested: by merge-train`. A fork PR fails closed: the runner never tests a fork head and `push-dest:` names no repo, so the tick settles its task failed and raises the retry / skip / stop alert instead.
- One open train per PR is judged by repository identity (the checkout origin's GitHub owner/repo), not by directory.
- While a workload owns an unsettled task, its first lane death, an intended exit with open work, and a runner failure on that task's PR are kept off needs-you (`trainRouted`, `trainRoutedRun`, `surface/src/errors.ts`): the task counts them. A failure on another PR, or one a settled task did not count, still shows.

**What the machinery enforces.**
- The test runner posts the terminal commit status `as2/full-suite` (success / failure / error) on the sha it fetched and tested, for every PR. Stale or superseded runs post nothing. Jo's one-time ruleset on main requires that status on an up-to-date head, so GitHub refuses any merge of an untested tree. Until the ruleset exists, every PR counts as production and asks Jo.
- P-11 row 6 refuses a lane's non-GET `gh api` call to statuses, check runs or check suites; the GraphQL status and check mutations; and any `gh api` argument the gate cannot read.
- The starter refuses train runs after Jo's `stop` until a new `train` word. An open question no longer holds the train.
- A `skip` cancels that PR's train slices, and the close check (`ClosePr.trainSkipped`, `surface/src/close-entry.ts`) treats the skipped PR as if it were closed.

**Stacked PRs.** A PR declares a dependency with a `Depends-on: #N` body line or by basing on another open PR's head branch. Before each PR, `merge-train.ts order` sorts the train with a stable topological sort, so a train with no dependencies keeps Jo's order. It prints the chain (e.g. `#101 → #106 · #110`), and the lane shows it in its messages and questions. The starter refuses a train PR whose body dependency is unmerged or whose base is not the default branch.

**The train tick (part 3, D10).** `surface/scripts/train-tick.ts`, run every 300 s by the launchd job `install/com.agent-system-2.train-tick.plist` (written and loaded by `bash install/install.sh --train-tick`, which resolves `gh`, `bun`, `omp`, `git`, `osascript` and `ctx` into the job's PATH, sets the ledger and `AGENT_SYSTEM_PROFILE`, and refuses when one is missing or `gh auth status` fails; `--train-tick=off` boots it out). Each run recomputes from the ledger and GitHub: it reads every train PR not yet terminal with `gh pr view` and, for each PR with an unsettled task on a same-repo branch, the head branch's push activity; writes each `settleTasks` settle once as `merge-train`; opens or reuses the fix workload (`openTrainFix`) for a task with no open owner; launches an autonomous owner not held live with `launch-requested: by merge-train` (once per task, again only after a runner result newer than its last launch); and wakes a train that is `actionable` and not held live (a settle, a new `train:`, an unworked PR, a `Depends-on` PR merged since the last lane exit, Jo's answer to a tick alert). An open question never stops it. A gh failure is a `train-error: tick …` entry, written again only when the reason changes, and retried next run. gh, the launcher and the notification are injected (`TickDeps`), so `surface/test/train-tick.test.ts` runs on a fake gh, a fake launcher and a temp ledger.

**Alerts (part 3, D9).** Each question on a train PR's slice is an alert: the lane's production merged / skip / stop, and the tick's own retry / skip / stop, raised (`raiseTwiceFailed`) when a PR's attempt 2 settled failed and Jo has not answered `retry` since. The send ladder (`trainAlertActions`): level 1 files `merge train: #<n> needs you (<reason>)` on thewolff/jo-issues with `gh issue create --label as2-train`; 4 h after it, while the question is open and the issue is not closed, level 2 comments mentioning `@thewolff`, adds `loud`, shows a macOS notification with sound and makes the needs-you line `LOUD` (`surface/src/errors.ts`); 8 h after it, level 3 does the same with `critical`; nothing after. Each send writes `train-alert: <q> level <n> sending`, its effects, then `sent` (MERGE_TRAIN_BY only); the issue body and each comment carry `<!-- train-alert <q> level <n> -->`, found before anything is created, labels are only added, and a `notified` marker keeps a retried send from notifying twice. Closing the issue is the ack (`train-alert: <q> acked`): no more re-sends, the question stays open and stalls nothing. Answering or withdrawing the question settles it and the tick closes the issue (`closed`). The level 1 marker is looked up in every as2-train issue: the REST listing `gh api repos/thewolff/jo-issues/issues -f labels=as2-train -f state=all --paginate --slurp`, through its last page and not the search index, so an issue created a moment ago is in it. A lookup that fails or reads an unexpected shape writes nothing durable: no issue is created and no `closed` is recorded, and the next run looks again; "no issue was filed" is concluded only from a complete listing.

**Retries.** The tick also wakes a released train for a PR it passed over with `train-error:` (a second runner error, a second refused merge, or a live owner lane), 15 min after the lane exited and then doubling per pass-over up to 4 h (`TRAIN_RETRY_BASE_MS`, `TRAIN_RETRY_MAX_MS`), and for each new head of a PR back from its owner that the train has not worked. A wake is recorded as `train-head-woken: pr <n> <sha>` when the launcher started a lane, and it is not the work: the head stays due until the train requests a run at it, writes `train-error: pr <n>` after the wake (that pass-over's retry then applies), returns a task at it, or the PR's slice is terminal. A head woken k times is due again once 15 min × 2^(k-1), capped at 4 h, has passed since the newer of that wake and the train's last lane end after it (`lane-exit:` or `launch-failed:`), so a lane that died before the work is relaunched, never on every tick. An alert's issue whose create outcome was uncertain is found again by its marker before any retry, and an issue filed in a crash window is closed when the question is settled.
