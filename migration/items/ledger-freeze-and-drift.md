**Built on branch `plumb/ledger-freeze-and-drift` (Plumb, 2026-10-12), PR #72.** From the ledger audit `~/agent-scratch/agent-system-2.0/ledger-audit/AUDIT.md` (findings A3-1, A2-3, A2-4, A5-1, A5-2, A1-1; writer identity, A2-1, is untouched pending Jo's ruling). On version 5, the module's own connection could rewrite a done slice's artifact (`completeSlice` twice: `done->done`), re-advance an acted-on message, change a closed workload's stakes, change stakes with no instruction, and close `wl-orchestrator`; and a file with triggers dropped opened and was written with no error. Version 6 (`ledger/schema.sql`) adds five triggers and no column: `slices_final`, `messages_acted_on_final`, `workloads_closed_final` (a final row's state stays and nothing else on it changes; a state change out of a final state is still the existing "illegal … transition"), `workloads_stakes_needs_instruction` (mirrors the mode-flip trigger: a `stakes: <stakes>` instruction since the last workload change; the surface already writes it first in the same transaction, `surface/src/input.ts` `case "stakes"`), and `workloads_standing_never_closes`. `Ledger.open` now sets `synchronous = FULL` on every read-write connection and compares the file's trigger set (names and SHA-256 of each statement) with the one schema.sql gives its version, refusing a drifted file unchanged (`LedgerTriggerDriftError`; `init.ts` exits 5); an extra trigger is refused too, since one can drop a write silently with `RAISE(IGNORE)` (tested), except a fault trigger a test names in `AGENT_SYSTEM_LEDGER_FAULT_TRIGGERS` (the lane-script fault tests open the faulted file from a second process; nothing else sets it). **Opening never upgrades (Jo's standing rule, Plumb's ruling on PR #72):** `Ledger.open` refuses a version-5 file with `LedgerNeedsMigrationError`, whose one line names the command; `bun run ledger/scripts/migrate.ts [path] [--force]` is the only upgrade (`migrateLedger`, the first entry of `MIGRATIONS` in `ledger/src/index.ts`, the trigger text taken from schema.sql). It is a no-op on version 6, refuses a drifted file (exit 5) and a file any live lane holds (exit 6, unless `--force`; checked early and again under the upgrade's write lock), writes a `VACUUM INTO` snapshot beside the file, prints the snapshot path and a shell-quoted lossless undo (drop the five triggers, `user_version = 5`) before the upgrade starts, refuses a file whose version changed between the check and the lock (exit 4), and upgrades in one `BEGIN IMMEDIATE`. **Refusals write nothing (Codex review of PR #72, B2):** every check before a write reads through `inspect`, a `mode=ro&readonly_shm=1` connection, because a read-write connection's close checkpoints a crash-left WAL into the file and a plain read-only one rewrites the `-shm` (both measured and pinned in the test); a non-empty `-wal` with no `-shm` is refused as unreadable, and a version-0 file that holds tables is refused rather than initialized. `copyProblem` accepts version 5 and 6 copies. `surface/scripts/invariants.ts` gains `ledger-health` (read-only `PRAGMA quick_check`, `PRAGMA foreign_key_check`, the same trigger comparison). Receipts: `ledger/test/freeze.test.ts` runs the audit's probe shapes through the version-5 module (`e472070`) and this one (accepted, then refused), and covers open-refuses-v5 byte-identical, migrate v5→v6 with its snapshot and undo run as printed by zsh and sh, migrate idempotent on v6, the held refusal early and under the lock, the version changing under the lock, the recovery lines printed before the upgrade, a crash-left WAL refused with file, `-wal` and `-shm` byte-identical, and the version-5 module refusing a version-6 file; each review fix's test fails on the code before it. **Deploy:** the staged procedure in `ledger/SCHEMA.md` (Versioning, "Deploy procedure for version 6"): stage the merged code in a separate clone; block launches and unload the backup job; drain and stop every writer (no live lease, `lsof` empty); migrate from the stage without `--force`, keeping the snapshot and undo; fast-forward the installed checkout and reload the backup job together; resume. A merge alone activates nothing; updating the installed checkout does. `~/agent-scratch/agent-system-2.0/ledger-freeze/deploy-v6.zsh` runs it (preview, typed confirm, log, saved undo). Rows are never rewritten by the upgrade. Not covered, recorded: re-advancing a non-final message to its own state (`delivered->delivered`) and a direct provenance insert through the module's connection both stay accepted (the audit's probes show both).
