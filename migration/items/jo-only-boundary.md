**Built on branch `wl/wl-mv654hoqwpfhmo-auth` (PR-C of workload `wl-mv654hoqwpfhmo`, production stakes, plan revision 14 at `~/agent-scratch/agent-system-2.0/wl-mv654hoqwpfhmo/PLAN.md` § 6, approved by Jo).** Some ledger rows carry Jo's authority: every `instructions` row authored `jo` and written by the surface (answers, withdrawals, mode flips, and the words `stakes:`, `ceiling:`, `rounds`, `stop-reviews`, approve / deny, `cap`, `switch`), and every control prefix only the surface writes (`plan:`, `done:`, `repo:`, `ceiling:`, `launch-requested:`, `lane-model:`, `cap:`, `switch:`, …). Until now a lane or hand could write any of them with the stamp `orchestrator-surface` from eval or a script, and the readers took it as Jo's word. `ledger/src/authority.ts` is now the one table of those rows (`AUTHORITY`, each with the reader that trusts it) and defines the predicate the readers are to use (`joAuthority`: author `jo` and stamp `orchestrator-surface`). No non-test reader calls `joAuthority` yet: the readers still check `author === "jo"` or compare `created_by` with the surface stamp inline, and moving them onto it is G4 (see the follow-up below). Row 11's direct channel (author `jo`, the lane's own stamp) is listed there as Jo's words, not Jo's authority.

**Threat model: accident grade.** In scope is an agent (a lane, a hand, or a process either starts) that by mistake, confusion or a bad instruction writes a row only Jo or the surface may write, or opens the ledger outside its tools. Out of scope: a deliberate same-uid attack that rewrites its env, drops a temp trigger it knows about, or brings its own SQLite build. The orchestrator agent is itself an agent with eval and bash, but its process *is* the surface (role `orchestrator`, no lane or workload id), so layer 1 does not cover it: for the orchestrator process the boundary is layers 2 and 3 only.

**Layer 1, the database.** `Ledger.open` gives a connection per-connection `TEMP` triggers on `main.workloads`, `main.slices`, `main.messages`, `main.questions`, `main.instructions` and `main.entries` (insert and update) when the process is an agent context (`AGENT_SYSTEM_ROLE` set to anything but `orchestrator`, or `AGENT_SYSTEM_LANE_ID` / `AGENT_SYSTEM_WORKLOAD_ID` set) and the file is in a live root (`liveRoots()` in `ledger/src/locality.ts`, now used outside test too; a root set that cannot be read counts as live). The triggers raise `Jo-only boundary: …` on any row stamped `orchestrator-surface` (`created_by`, or `changed_by` on updated tables); on any `author = 'jo'` instruction that is not row 11's shape (kind `instruction`, channel `direct`, no question, stamped with the connection's own `AGENT_SYSTEM_LANE_ID`); and on any `answer` row, whatever its author. The trigger text is built at open from the process's `AGENT_SYSTEM_LANE_ID`, written into it as an SQL literal. They sit under `ledger.db` and `ledger.write(fn)`, so the raw connection is covered, not only the helper methods. Temp triggers write nothing to the file: no `sqlite_master` row, no schema change. No option removes them; the open option `authority: "enforce"` only adds them, which the boundary's own tests use on a scratch file. Throwaway ledgers outside a live root get no triggers in any process, so tests that write surface-stamped rows, a lane-run chaos on its scratch ledger and seeded proofs keep working; every lane-stamped write (the lane tools, the runner's `lane-runner` rows and its ceiling-question withdrawals, row 11 as the lane itself) stays allowed on the live file.

**G2, built: an agent never answers a question.** Before G2 a lane could answer its own question with any author except `jo` (`answerQuestion(q, { author: "lane-x", channel: "direct" })` was written), and `resolutions` in `surface/src/launch.ts` takes any `answer` row as the question's resolution, so a lane could un-gate itself with no Jo. Layer 1 now refuses every `answer` insert or update on an agent connection to a live ledger, whatever the author. Withdrawals stay allowed: the runner's `withdrawCeilingQuestions` in `surface/scripts/lane.ts` writes one as `lane-runner`. The non-test writers of an answer are `surface/src/input.ts` (`apply`, the pair-taken path) and `surface/src/orchestrator-question.ts` (`answerOrchestratorQuestion`); both run in the orchestrator's process through the surface rows, which are inert in lanes and hands (`surface/index.ts` header), so no agent-context code path writes an answer.

**G3, built: row 11's shape is the lane's own.** Before G3 the exemption for row 11's shape did not check the stamp, so a lane could write Jo's words stamped as another lane or as machinery (`escalation`, `lane-runner`), and `joInstructionsFor` delivered them to the next lane as Jo's. The exemption now also requires `created_by` to equal the connection's `AGENT_SYSTEM_LANE_ID`, which is how row 11 writes it (`recordJoInstruction` in `gates/src/rows/r11-jo-instruction.ts`, `by: input.laneId`, the session's `AGENT_SYSTEM_LANE_ID`). A connection with no lane id (a hand's own process, another agent context) gets no row 11 shape.

**Premise.** This install's ledger is at the default path (`~/.agent-system-2/ledger.db`) or named by `AGENT_SYSTEM_LEDGER_DB` in the lane's environment. Those, with the test preload's `AS2_TEST_*` names, are the only inputs that change the root set, and layer 2 refuses an agent setting them.

**Layer 2, the gate.** P-11 row 10 (`gates/src/rows/r10-raw-ledger.ts`, with detectors in `gates/src/eval-code.ts`) refuses, for every role, with a reason naming the "Jo-only boundary": eval or inline (`bun -e`) code, or a script an interpreter runs (G1 below), that loads the ledger module (`ledger/src`, by import, dynamic import or require); JS code in eval, inline code or a script outside every git repository that loads any module by a specifier that is not one literal string (`import(p)`, `require(p)`, `require` aliased, a `createRequire` result called with a computed path); code that names a `ledger.db` in an open or a write, or loads a database module and names a path under `.agent-system-2/`; `sqlite3` without `-readonly` on a `ledger.db` or under `.agent-system-2/`; and any set, unset or override of `AGENT_SYSTEM_ROLE`, `AGENT_SYSTEM_LANE_ID`, `AGENT_SYSTEM_WORKLOAD_ID`, `AGENT_SYSTEM_LEDGER_DB` or an `AS2_TEST_*` name (a prefix or `env` assignment, `export`, `declare`, `unset`, `env -u`, `env -i`, the bash tool's `env` input; in eval `process.env.X = …`, `delete process.env.X`, `os.environ[…] = …`, `os.environ.pop(…)`, `putenv`). Reading stays allowed: `sqlite3 -readonly <ledger>` with SELECT, `echo $AGENT_SYSTEM_ROLE`, `process.env` reads, and `bun test <file>`.

**G1, built: scripts are read (review round 1 folded in).** Before G1 row 10 read only eval and inline code, so `bun forge.ts`, `bun run forge.ts`, `node forge.js`, a heredoc that writes the script and runs it in one call, and a computed `import()` all passed.

What is read, at gate time, and judged as eval code is in its interpreter's family: the program file of `bun <file>`, `bun run <file>`, `node <file>`, `tsx <file>`, `ts-node <file>`, `python`/`python3 <file>`, `perl <file>`, `ruby <file>`, `deno run|serve|watch <file>` and `deno <file>`; every module an option loads before it (`--preload`/`-r`, `--require`, `--import`, `--loader`, deno's `--preload`); the file `bun x`, `bunx` or `npx` runs through `tsx`, `ts-node`, `node` or `bun`; and the command line `bun exec '…'` or `npx -c '…'` runs, judged as a bash call of its own. The interpreter's options before the program are skipped (`--smol`, `--bun`, `--watch`, `--hot`, `--silent`, `--`, `--env-file[=]`, `--title x`, node's `--no-warnings`, python's `-u -W x`, …; an option the gate does not list is a flag with no value), and `--cwd <dir>` (bun) or `-C <dir>` (ruby) moves where a relative program resolves. A program word with an expansion is read at the value the session's environment, with the bash tool's `env` input over it, gives it (`"$AS2_SCRATCH/forge.ts"`, `${HOME}/f.ts`, `~/f.ts`); one the gate cannot resolve (a command substitution, an unset variable) is refused. bun and node also get the extension they add to a bare path. Up to 256 KiB of a file is read; a file that is larger, unreadable, or written in the same call from text the gate cannot see (a `cp`, `curl -o`) is refused. Any heredoc, herestring or `echo`/`printf` text the same call writes into the file is read with it, and python's inline forms (`python3 -c '…'`, `python3 - <<EOF`) are read as inline code, as before. Python, Perl and Ruby files get the ledger-path rules (a `ledger.db` named in an open or connect, a database module plus `.agent-system-2/`); the computed-load rule is JS only, and applies to eval, inline code and scripts outside every git repository (scratch), never to a script inside a repository (another product's build script doing `await import(path)`). Text that only mentions `require(` inside a template literal is not a load.

Not read: `bun test` and bun's other subcommands (`install`, `build`, …), deno's other subcommands, python `-m`, php and osascript files; a bare name that is no file (`bun run typecheck`, a package script, a preload's package name); a missing file nothing in the call is seen to write (it runs nothing); the ledger module's own `ledger/scripts/`; and any file under a directory named `scripts` anywhere in an agent-system-2.0 checkout or lane worktree, or under its `bin/` (the root is the nearest directory holding `ledger/schema.sql` and a `.git`), so `bun surface/scripts/invariants.ts`, `lane.ts` and the cross-model-review panel (`skills/cross-model-review/references/panel/scripts/panel.ts`, which lanes run) still run.

Limits, stated: (1) a scratch clone of this repository has the same shape as a checkout, so its `scripts/` and `bin/` files run unread, and a model may edit a scratch clone; (2) `bun test` is unread because the test preload keeps test files off the live roots, but that preload is wired only by the `bunfig.toml` at this repository's root, module roots and test directories, so `bun test` run under a directory with no such bunfig runs its files with the real HOME, unread; (3) accident grade: a transitive import, a script a writer the gate does not parse produces in the same call, code obfuscated past a static scan, and a Perl or Ruby file's computed module load (`require $x`) are not seen. The `lane-<pid>` lane id a gate session falls back to (`gates/src/session.ts`, the `lane-${process.pid}` fallback) is never a launched lane's: both lane spawn sites set `AGENT_SYSTEM_LANE_ID` (`surface/scripts/lane.ts` through `laneSpawnEnv`, `surface/src/launch.ts` `laneEnv`), and a session started without it gets a G3 trigger with no lane id, so its row-11 write is refused (fails closed) rather than stamped `lane-<pid>`.

**Layer 3, integrity commands need Jo at a terminal: merge condition, not built here.** `migrate` (PR #72) and `restore` (PR #74) must refuse unless stdin is a TTY and Jo types the ledger path back; lanes run `omp --mode rpc` with no TTY. Neither script is on `origin/main` at `21699ad` (`ledger/scripts/` holds `backup.ts` and `init.ts` only), so the TTY check and the typed path are a merge condition of #72 and #74: neither merges without them.
