**Built on branch `wl/wl-mv654hoqwpfhmo-auth` (PR-C of workload `wl-mv654hoqwpfhmo`, production stakes, plan revision 14 at `~/agent-scratch/agent-system-2.0/wl-mv654hoqwpfhmo/PLAN.md` § 6, approved by Jo).** Some ledger rows carry Jo's authority: every `instructions` row authored `jo` and written by the surface (answers, withdrawals, mode flips, and the words `stakes:`, `ceiling:`, `rounds`, `stop-reviews`, approve / deny, `cap`, `switch`), and every control prefix only the surface writes (`plan:`, `done:`, `repo:`, `ceiling:`, `launch-requested:`, `lane-model:`, `cap:`, `switch:`, …). Until now a lane or hand could write any of them with the stamp `orchestrator-surface` from eval or a script, and the readers took it as Jo's word. `ledger/src/authority.ts` is now the one table of those rows (`AUTHORITY`, each with the reader that trusts it) and defines the predicate the readers are to use (`joAuthority`: author `jo` and stamp `orchestrator-surface`). No non-test reader calls `joAuthority` yet: the readers still check `author === "jo"` or compare `created_by` with the surface stamp inline, and moving them onto it is G4 (see the follow-up below). Row 11's direct channel (author `jo`, the lane's own stamp) is listed there as Jo's words, not Jo's authority.

**Threat model: accident grade.** In scope is an agent (a lane, a hand, or a process either starts) that by mistake, confusion or a bad instruction writes a row only Jo or the surface may write, or opens the ledger outside its tools. Out of scope: a deliberate same-uid attack that rewrites its env, drops a temp trigger it knows about, or brings its own SQLite build. The orchestrator agent is itself an agent with eval and bash, but its process *is* the surface (role `orchestrator`, no lane or workload id), so layer 1 does not cover it: for the orchestrator process the boundary is layers 2 and 3 only. **What this PR builds is a set of tripwires at that grade, not a hard boundary** (Jo: `narrow`, q-mvglmwzl4be5ts, on review round 3): layer 1 holds only for writers that go through the ledger module, and layer 2, G1 included, catches the forms it reads and states the routes it does not (the limits below). The hard boundary for ledger integrity and Jo's authority is the follow-up **ledger writer authentication** (G5 below: persistent triggers in the ledger file, plus a connection capability the fence denies agents).

**Layer 1, the database.** `Ledger.open` gives a connection per-connection `TEMP` triggers on `main.workloads`, `main.slices`, `main.messages`, `main.questions`, `main.instructions` and `main.entries` (insert and update) when the process is an agent context (`AGENT_SYSTEM_ROLE` set to anything but `orchestrator`, or `AGENT_SYSTEM_LANE_ID` / `AGENT_SYSTEM_WORKLOAD_ID` set) and the file is in a live root (`liveRoots()` in `ledger/src/locality.ts`, now used outside test too; a root set that cannot be read counts as live). The triggers raise `Jo-only boundary: …` on any row stamped `orchestrator-surface` (`created_by`, or `changed_by` on updated tables); on any `author = 'jo'` instruction that is not row 11's shape (kind `instruction`, channel `direct`, no question, stamped with the connection's own `AGENT_SYSTEM_LANE_ID`); and on any `answer` row, whatever its author. The trigger text is built at open from the process's `AGENT_SYSTEM_LANE_ID`, written into it as an SQL literal. They sit under `ledger.db` and `ledger.write(fn)`, so the module's own connection handle is covered, not only its helper methods. Temp triggers write nothing to the file: no `sqlite_master` row, no schema change. No option removes them; the open option `authority: "enforce"` only adds them, which the boundary's own tests use on a scratch file. Throwaway ledgers outside a live root get no triggers in any process, so tests that write surface-stamped rows, a lane-run chaos on its scratch ledger and seeded proofs keep working; every lane-stamped write (the lane tools, the runner's `lane-runner` rows and its ceiling-question withdrawals, row 11 as the lane itself) stays allowed on the live file. **Layer 1 covers only writers that go through the ledger module.** The triggers are installed by `installBoundary` in `ledger/src/authority.ts`, which only `Ledger.open` calls. A raw `bun:sqlite` connection (or Python's `sqlite3`, or any other SQLite client) opened on the ledger file outside the module never installs these TEMP per-connection triggers, so G2's answer refusal, G3's stamp check and the surface-stamp refusal do not apply to it. Stopping such a connection is left to layer 2, a tripwire, until the follow-up's persistent triggers.

**G2, built: an agent never answers a question.** Before G2 a lane could answer its own question with any author except `jo` (`answerQuestion(q, { author: "lane-x", channel: "direct" })` was written), and `resolutions` in `surface/src/launch.ts` takes any `answer` row as the question's resolution, so a lane could un-gate itself with no Jo. Layer 1 now refuses every `answer` insert or update on an agent connection to a live ledger, whatever the author. Withdrawals stay allowed: the runner's `withdrawCeilingQuestions` in `surface/scripts/lane.ts` writes one as `lane-runner`. The non-test writers of an answer are `surface/src/input.ts` (`apply`, the pair-taken path) and `surface/src/orchestrator-question.ts` (`answerOrchestratorQuestion`); both run in the orchestrator's process through the surface rows, which are inert in lanes and hands (`surface/index.ts` header), so no agent-context code path writes an answer.

**G3, built: row 11's shape is the lane's own.** Before G3 the exemption for row 11's shape did not check the stamp, so a lane could write Jo's words stamped as another lane or as machinery (`escalation`, `lane-runner`), and `joInstructionsFor` delivered them to the next lane as Jo's. The exemption now also requires `created_by` to equal the connection's `AGENT_SYSTEM_LANE_ID`, which is how row 11 writes it (`recordJoInstruction` in `gates/src/rows/r11-jo-instruction.ts`, `by: input.laneId`, the session's `AGENT_SYSTEM_LANE_ID`). A connection with no lane id (a hand's own process, another agent context) gets no row 11 shape.

**Premise.** This install's ledger is at the default path (`~/.agent-system-2/ledger.db`) or named by `AGENT_SYSTEM_LEDGER_DB` in the lane's environment. Those, with the test preload's `AS2_TEST_*` names, are the only inputs that change the root set, and layer 2 refuses an agent setting them.

**Layer 2, the gate.** P-11 row 10 (`gates/src/rows/r10-raw-ledger.ts`, with detectors in `gates/src/eval-code.ts`) refuses, for every role, with a reason naming the "Jo-only boundary": eval or inline (`bun -e`) code, or a script an interpreter runs (G1 below), that loads the ledger module (`ledger/src`, by import, dynamic import or require); JS code in eval, inline code or a script outside every git repository that loads any module by a specifier that is not one literal string (`import(p)`, `require(p)`, `require` aliased, a `createRequire` result called with a computed path); code that names a `ledger.db` in an open or a write, or loads a database module and names a path under `.agent-system-2/`; `sqlite3` without `-readonly` on a `ledger.db` or under `.agent-system-2/`; and any set, unset or override of `AGENT_SYSTEM_ROLE`, `AGENT_SYSTEM_LANE_ID`, `AGENT_SYSTEM_WORKLOAD_ID`, `AGENT_SYSTEM_LEDGER_DB` or an `AS2_TEST_*` name (a prefix or `env` assignment, `export`, `declare`, `unset`, `env -u`, `env -i`, the bash tool's `env` input; in eval `process.env.X = …`, `delete process.env.X`, `os.environ[…] = …`, `os.environ.pop(…)`, `putenv`). Reading stays allowed: `sqlite3 -readonly <ledger>` with SELECT, `echo $AGENT_SYSTEM_ROLE`, `process.env` reads, and `bun test <file>` of this repository's test files from the checkout, a module directory or a `git archive` copy of it, whose bunfig.toml isolates the ledger, or with that tree's isolate preload named by `--preload`/`-r`. Layer 2 is a static reading of command and code text at gate time: a tripwire for the accident-grade forms, not a boundary a model that means to pass it cannot pass.

**G1, built: a tripwire that reads scripts (review rounds 1, 2 and 3 folded in).** Before G1 row 10 read only eval and inline code, so `bun forge.ts`, `bun run forge.ts`, `node forge.js`, a heredoc that writes the script and runs it in one call, and a computed `import()` all passed. G1 is a tripwire, not a hard boundary: it reads the files a command is seen to run and refuses the accident-grade forms, and the limits stated below are routes it does not see. Round 3's three security findings are among them, stated rather than fixed (Jo: `narrow`). The hard boundary is the follow-up, ledger writer authentication (G5).

What is read, at gate time, and judged as eval code is in its interpreter's family: the program file of `bun <file>`, `bun run <file>`, `node <file>`, `tsx <file>`, `ts-node <file>`, `python`/`python3 <file>`, `perl <file>`, `ruby <file>`, `deno run|serve|watch <file>` and `deno <file>`; every module an option loads before it (`--preload`/`-r`, `--require`, `--import`, `--loader`, deno's `--preload`) and every `preload` in the `bunfig.toml` of the working directory, or of `--config=<file>`, when bun runs a file or inline code (bun reads no other bunfig: a parent directory's, `~/.bunfig.toml` and `$XDG_CONFIG_HOME/.bunfig.toml` were not loaded, live, bun 1.3.14); the module `python -m <name>` runs from the working directory (`<name>.py`, a package's `__init__.py` and `__main__.py`); the command line of a package.json script, found in the nearest package.json at or above the directory as bun and npm find it, with its `pre`/`post` scripts, for `bun run <name>`, `bun <name>` (a script of that name runs before a file of that name), `npm run|start|test|restart|stop`, and `node --run <name>`, judged as a bash call of its own; the file `bun x`, `bunx`, `npx` or `npm exec` runs through `tsx`, `ts-node`, `node` or `bun`, and, for any other package, every argument naming an existing file (`bunx jiti f.ts`, `bunx vite-node f.ts`, `bunx zx f.js`; the fail-closed choice over a list of file-running packages, so a formatter handed a file that writes the ledger is refused too); and the command line `bun exec '…'` or `npx -c '…'` runs. `bun test` reads its `-r`/`--preload` modules, its bunfig's preloads, and every test file it runs (each `./`, `../` or `/` path argument, and the `*.test.*`/`*_test.*`/`*.spec.*`/`*_spec.*` files under the working directory whose path holds a filter argument). A test file of an agent-system-2.0 tree (the nearest directory holding `ledger/schema.sql`: a checkout, a lane worktree, or a `git archive` copy with no `.git`) runs unread only when a preload of the run, from its bunfig or a `--preload`/`-r` on the command line, is that tree's `ledger/test/isolate-preload.ts`, and that preload is the checkout's own file (below) or, in a tree git does not track, byte for byte the gate's own isolate preload beside the gate's own `ledger/src/locality.ts` (the one module it loads, with no other file that import could resolve to); such a preload runs unread too. A call that writes either file gets no isolation. Test isolation is recognised apart from the trust exemption (round 3, finding 4): it lets a tree's test files run unread in that run and trusts nothing else in the tree. The files code loads by a literal path are read the same way, to four files deep (a load deeper than that is refused, not read): JS `import`, `import()` and `require()` of a `/`, `./`, `../`, `~/` or `file://` specifier (a package name is not read); Python `exec`/`compile` of one file read (`open(p).read()`, `Path(p).read_text()`), `runpy.run_path`, `execfile`, `spec_from_file_location`, `SourceFileLoader`, `load_source`, the eval tool's `%load`, a module imported from the code's directory or a directory it puts on `sys.path`, and the literal code `exec` runs. Versioned and variant runtime names are interpreters too (`node22`, `bun-canary`, `bun-profile`, `python3.12`). The interpreter's options before the program are skipped (`--smol`, `--bun`, `--watch`, `--hot`, `--silent`, `--`, `--env-file[=]`, `--title x`, node's `--no-warnings`, python's `-u -W x`, …; an option the gate does not list is a flag with no value), and `--cwd <dir>` (bun) or `-C <dir>` (ruby) moves where a relative program resolves. A program word with an expansion is read at the value the session's environment, with the bash tool's `env` input over it, gives it (`"$AS2_SCRATCH/forge.ts"`, `${HOME}/f.ts`, `~/f.ts`); one the gate cannot resolve (a command substitution, an unset variable, a `for` loop's variable) is refused. bun and node also get the extension they add to a bare path. Up to 256 KiB of a file is read; a file that is larger, unreadable, or written in the same call from text the gate cannot see (a `cp`, `curl -o`) is refused. Any heredoc, herestring or `echo`/`printf` text the same call writes into the file is read with it, and python's inline forms (`python3 -c '…'`, `python3 - <<EOF`) are read as inline code, as before. Python, Perl and Ruby files get the ledger-path rules (a `ledger.db` named in an open or connect, a database module plus `.agent-system-2/`). The computed-load rule applies to eval, inline code and scripts outside every git repository (scratch), never to a script inside a repository (another product's build script doing `await import(path)`): in JS an `import()`/`require()` whose specifier is not one literal string, and `eval`/`Function` on code that is not one literal string; in Python an `exec`, `runpy`, `importlib` or `sys.path` call whose target is not a literal. Text that only mentions `require(` inside a template literal is not a load. Refused: `deno task` (the gate does not read deno.json), and npm with `--prefix` or a workspace option.

Not read: bun's other subcommands (`install`, `build`, …), npm's other commands (`install` and its lifecycle scripts included), deno's other subcommands, php and osascript files; a bare name that is no file and no package.json script (a bin, a preload's package name); a module `python -m` or an import finds outside the working directory and the directories the code puts on `sys.path` (the standard library, an installed package); a missing file nothing in the call is seen to write (it runs nothing); and a checkout's own files: in an agent-system-2.0 checkout or lane worktree (the root is the nearest directory holding `ledger/schema.sql` and a `.git`), every file git tracks, every file under a directory named `scripts` anywhere in it or under its `bin/`, and the ledger module's `ledger/scripts/`. Limits, stated: (1) a scratch clone of this repository has the same shape as a checkout, so its tracked, `scripts/` and `bin/` files run unread, and a model may edit a scratch clone; a `git archive` copy (no `.git`) gets no trust exemption, but its test files run unread in a `bun test` run isolated by its own isolate preload, whatever a model wrote into them before the call; (2) the test preload (`ledger/test/isolate-preload.ts`) points only the environment's ledger paths (`HOME`, `AGENT_SYSTEM_LEDGER_DB`, `AS2_TEST_*`) at a scratch root, so a checkout's own test file that names the live ledger by an absolute literal path is not stopped by it; such a file is reviewed code, the grade of a script under `scripts/`, while an untracked test file in the checkout is read; (3) `bun test` with a filter the gate cannot resolve (a loop variable) is refused, and one under a directory of more than 50,000 entries is refused rather than walked; (4) a package.json script reached by a route the gate does not model runs unread: npm's `install` lifecycle scripts, `yarn`/`pnpm`, `bun run --filter` across workspaces, and a script that itself runs a file through a package the gate reads only by argument; (5) Python modules and `sys.path` entries set outside the code (`PYTHONPATH`, a `.pth` file, `PYTHONSTARTUP`) are not followed; (6) accident grade: a JS import of a package name (a local `node_modules` package the model wrote), a script a writer the gate does not parse produces in the same call, code obfuscated past a static scan, and a Perl or Ruby file's computed module load (`require $x`) are not seen; a load by a literal path more than four files deep is not read but refused.
