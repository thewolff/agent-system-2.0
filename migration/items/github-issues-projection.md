**What it does.**

- **One issue per open workload.** Title `wl-<id> — <first line of the brief, 80 chars>`. The body's machine block sits between `<!-- as2:begin -->` and `<!-- as2:end -->`: status, stakes, mode, holder (or `nobody — waiting`), ceiling used, slice counts, open question ids with their first line, each PR's URL and state, and the ledger seq it was rendered from (`render.ts`). Text Jo writes outside the markers is kept. Labels come from the ledger and the PR set only: `as2`, then `running` or `waiting` while open, `question` while a question is open, `awaiting-merge`, `unmerged`. Missing labels are created once per repo.
- **Outbox.** Every surface poll (60 s) fires one tick, fire-and-forget: no turn, wake push or close waits on it. The tick takes a claim in the sidecar `issues.db` (beside the ledger, so `~/.agent-system-2/issues.db` for the live ledger), so two orchestrator sessions on one ledger never push twice. Ingest reads provenance past the sidecar's cursor (lease renewals and `wl-orchestrator` left out) and marks those workloads' links dirty; it is local, so it runs while the switch is off too. The first tick after the first `issues on` seeds one dirty link per open workload a tracker applies to. Pushes then drain the dirty links. Every call is counted before it runs, **20 per tick and 300 per rolling hour, per tracker** (GitHub and Linear each have their own count; `issues.perTick` / `issues.perHour`). A call over a cap is not made and is never a failure. A failed push backs off (`min(60 s · 2^fails, 1 h)`); after 10 failures in a row (`parkAfterFails`) the link is parked with one notice until the reconciler finds drift on it. Once an hour `gh api rate_limit` is read; under 500 core calls left, GitHub work pauses.
- **Reconciler.** Every 60 minutes (`reconcileEveryMin`) while on, it compares every `as2` item on each tracker with the render of the ledger now (title, machine block, labels, state). It records one entry on `wl-orchestrator`: `issues-drift: <N> at <iso>` followed by one line per difference (the first 20), the ignored intake count, and any turn-end notices since the last run. When a read failed, the rate limit was low or the budget ran out, it records `issues-drift: unknown (<why>) at <iso>`: never 0. Each drifted item is marked so the next push re-reads the remote and repairs it, even with no ledger change. An open `as2` issue naming no ledger workload is reported, never closed. An open `as2` item naming a closed workload with no item linked, on that workload's tracker, is adopted (one drift line) and closed by the next push as the render says; one naming a closed workload that holds another item is one line, left open. Jo reopening a closed workload's issue is closed again with one comment: `wl-… is closed and cannot reopen; file a new issue`. Drift or unknown on two runs in a row gives one notice. `bun surface/scripts/issues.ts check` runs the same comparison read-only.
- **`Closes #N` in PR bodies.** Machinery adds it; the model never writes it. Each tick scans the repo's open PRs and maps each one to a workload by a bound head branch or a `test-requested:` number. Every mapped PR into the default branch whose workload's issue is on GitHub gets `<!-- as2 -->` + `Closes #N` appended with `gh pr edit --body`, once. A decision-log PR that `publishEntry` creates at a close carries the same footer in its `gh pr create` body, with no extra call. That happens only when the switch is on and the workload's issue is on GitHub in the repo the PR is created in.
- **Merge and close.** A closed workload with an open PR in its set keeps its issue open with `awaiting-merge`. The issue closes `completed` when a PR merges, either by GitHub's own `Closes #N` or, for a non-default-base PR, a PR merged before any scan saw it, or a Linear item, by the tick seeing the PR merged. The first merge wins: a second PR still open never reopens it. Every PR closed unmerged ⇒ closed `not planned` with `unmerged`. A workload with no PR closes its issue at the ledger close (`not planned` only when every slice was cancelled and none done). An issue is never created only to be closed: a workload opened and closed between pushes gets none.
- **Intake.** Every 5 minutes (`intakeEveryMin`) while on, the issues Jo files on `thewolff/jo-issues` (`issues.intakeRepo`; Jo chose it in q-mv92ac7xt75v5s / in-mv92q6ft9t9af4; without the key intake reads the first exact GitHub repo in `trackers`) are read oldest first. An issue labelled `plumb` or `as2-train` (`issues.intakeSkipLabels`, default `plumb`, `as2-train`; in-mv93e832mquneo) is skipped before any proof call: Plumb and the merge train's alerts file there as `thewolff` too, and a machinery-filed issue never becomes a Jo instruction. It gets no label and no comment, and it is counted as ignored (`labelled plumb`, `labelled as2-train`) in the drift entry. The proof checks the labels again. An issue becomes a Jo input only when every PLAN § 6.2 rule holds:
  - the author login is `issues.jo` (`thewolff`) with author association `OWNER`;
  - it was filed at or after the `issues on` entry;
  - its body carries no `<!-- as2:begin -->` projection block;
  - it was never transferred in;
  - every body edit and rename is by Jo, with nothing past one page of either (nor of labels).

  The accepted issue becomes one instruction on `wl-orchestrator` (`github-issue #N by thewolff <createdAt>: <title>` + body, author `jo`, channel `surface`, the shape `orchestrator_record_instruction` accepts), and Ilex is told `Jo filed issue #N → input in-…: <title>`. The issue then gets the `intake` label and one comment, `recorded as in-… on wl-orchestrator`. Before the first label, intake makes the `intake` label on the intake repo once, with counted calls (`intake_labels_created:<repo>` in the sidecar), because the projector never makes its labels on a repo it files no issues on. Comments are never read. Anything else is ignored: the ledger gets nothing, and the reason is counted in the drift entry. An issue on jo-issues is never a projected issue: a workload opened with a brief that quotes the `in-…` id gets its own issue on its repo. The PLAN § 6.2 binding, where that workload takes over the intake issue, applies only when the intake repo is the workload's issues repo (as it is with no `intakeRepo` key). Row 6 now reserves `gh auth switch|token|login|logout|refresh|setup-git`, `gh auth status --show-token`, `GH_TOKEN=` / `GITHUB_TOKEN=` assignments and keychain password reads (`security find-…-password`) from lanes and hands; plain `gh auth status` stays free.
- **Turn end.** At every Ilex turn end (`agent_end`, not continuing), each workload with provenance since the previous turn end gets a `turns` row in the sidecar, and its link is marked dirty with priority, so the tick started right then pushes it first. Two ticks later, a row whose link has not been pushed to that workload's seq gives one notice, `issue for wl-… not updated after turn <time>: <reason>` (budget, backoff, parked, tracker down, missing key), and one line in the next drift entry. It is never retried beyond the link's own backoff.

**Tracker routing** (`issues:` block of `profile/config.yml`).

- `trackers` is an ordered list matched against the workload's `repo:` checkout's origin owner/repo; the first match wins. `thewolff/agent-system-2.0` goes to GitHub issues on that repo. `ContextPress/*` goes to Linear team ENG, through Linear's GraphQL API with `LINEAR_API_KEY` from the surface's environment. The key goes only in the Authorization header, never in argv, and is redacted from every error and notice. Any other repo (for example `thewolff/jo-wolff-plugins`) is not projected.
- `overrides` seeds `wl-mv5jz4vewt8mbk: linear:ENG`: the SEO audit's repo is agent-system-2.0 but its subject is newdle.com, so it is never filed on GitHub.
- Jo's typed word `tracker <wl-id> github|linear <TEAM>|none` moves one open workload. It writes the instruction and a `tracker: <wl-id> <kind> [<team>] by <in-…>` entry on that workload in one transaction. Precedence: newest `tracker:` entry, then `overrides`, then `trackers`. A move closes the old item `not planned` with one comment naming the new place. It also strips the machinery's own footer from that workload's open PRs, and only when the footer is exactly the body's suffix; anything else is left and counted as drift. The next push creates the new item. The word is refused, writing nothing, for a closed workload, `wl-orchestrator`, an unknown id or a malformed form.
- On Linear the state maps by workflow type: open ⇒ In Progress, `awaiting-merge` ⇒ In Review, `completed` ⇒ Done, `not planned` ⇒ Canceled. The labels are the same, except `intake`. **A Linear workload has no intake and no PR footer**: its PR bodies are never edited, and its item closes when the tick sees the PR merged. Linear items are written with Jo's own key, so they show Jo as author.
- Linear rewrites the markdown it stores (it re-escapes and re-indents list lines), so the machine block it returns never equals the render byte for byte. Each write keeps a hash of the block Linear returned (`remote_hash` in the sidecar), and the reconciler compares the block it reads against that, not against the render. A link written before this had none and drifts once; the forced push repairs it and stores the hash. GitHub returns the body as written, so its comparison is unchanged.

**The switch: `issues on` / `issues off`.** Jo's typed word writes an instruction and `switch: issues on|off orchestrator by <in-…>` on `wl-orchestrator` in one transaction (the switch registry's shape, so wl-mv654hoqwpfhmo's registry can read these same entries when it lands). The newest entry is the state; with none the switch is **off**, so it is off by default. Off stops every call the projection makes: pushes, label creation, the PR scan and its footer edits, reconcile, intake, and the footer in a `publishEntry`-created PR body. It does **not** stop the close's own decision-log publication: the `git push` of `wl/<id>` and its `gh pr create` run as on main. While off, ingest keeps marking links locally and turn rows settle `not-projected`; `on` resumes from the dirty set.

Full code rollback: `git revert -m 1 <merge commit>`; there is no ledger schema change.

**Residuals.**

- Jo-proof for intake is accident grade. A same-uid process that deliberately reaches the `thewolff` token another way can author as Jo. The hard boundary is Jo's `gh auth logout -u thewolff` (rollout step 4).
- The `plumb` and `as2-train` skips trust the label. Plumb and the merge train author as `thewolff`, so a machinery issue filed without its label passes the proof and becomes a Jo input, and an issue Jo labels `plumb` or `as2-train` is skipped.
- Intake keeps one cursor and one verdict table, keyed by issue number, for one repo. Changing `issues.intakeRepo` after intake has run would match the new repo's numbers against the old repo's verdicts. Clear the sidecar's `intake` rows and its `intake_after` state first.
- Projected GitHub issues are authored by `thewolff-engineer`. The hourly drift entry adds 24 entries a day to `wl-orchestrator`.
- A PR opened and merged within one poll (about 60 s), before any scan saw it, merges without the footer. The issue then closes at the next push from the PR's MERGED state, not by GitHub.
- A PR that merges while its workload is still open closes the issue on GitHub. The next push reopens it (the ledger says open) and it closes for good at the ledger close: one visible reopen.
- No backfill: a workload already closed when the switch first goes on never gets an issue, and MIGRATION items with no workload get none.
- Reopening a closed workload's issue is not intake. It is drift, repaired back to closed with one comment.
- Routing is by repo origin. Exceptions need Jo's `tracker` word or a config override.
- There is no Linear intake. Jo's `LINEAR_API_KEY` is inherited by every process Jo's shell starts, lanes and hands included, before and after this change. The projection adds no holder and never logs it; narrowing it is a change to Jo's shell setup.
- The turn-end range runs from the previous turn end to this one, so lane writes between two turns also count. That over-covers and never under-covers.
- The reconciler shares the per-tick budget. It runs as a tick phase after the push, inside the same claim and the same 20-per-tick / 300-per-hour counts, so a heavy push tick can leave it short, and it then records `unknown (…)`. The PR scan costs one GitHub call per scanned repo per tick, and a tick runs at every poll (60 s) and at every Ilex turn end. With agent-system-2.0 and one ContextPress repo scanned, that is about 120 calls an hour plus two per turn, before any push. The smoke ran a 10 s poll with a turn at every poll, so its scans alone overran the hour and the reconciler recorded `unknown (… github budget)` instead of a count. Each further ContextPress repo with an open workload adds about 60 an hour.
- The first hour after `issues on` is spent seeding. Seeding about 55 issues used the whole 300-call GitHub hour in about 6 minutes in the smoke (adopt search, create, labels and PR-set reads per workload), so pushes, intake and the reconciler's GitHub reads wait until the oldest calls leave the rolling hour; the hourly drift entry says `unknown (github budget)` meanwhile.
- A removed `Closes #N` footer is put back. Machinery owns the footer (PLAN § 5), so a scan that finds it missing from a mapped PR into the default branch re-adds it (one view and one edit per removal, inside the caps). There is no per-PR opt-out: to keep a PR from closing its issue, retarget the PR or switch the projection off.
- A PR opened more than 24 hours after a workload closed is not discovered on a repo routed by an owner glob (the `ContextPress/*` Linear route). A closed workload whose item is closed and holds no merged PR keeps its repo in the PR scan for 24 hours after the close (`LATE_PR_WINDOW_MS`), long enough for the decision-log PR that `publishEntry` opens at close; exact-repo rules (`thewolff/agent-system-2.0`) are scanned every tick and do not have this limit. A later PR on such a repo leaves the item as it was until the workload's ledger changes again.
- An open `as2` issue naming a closed workload with no item linked is not read on a GitHub repo that only an owner-glob rule routes and no open or linked workload is on: a glob names no repo to list, so the reconciler neither reports nor adopts it until a workload there opens or links (exact repos, overrides, `tracker:` entries and Linear teams are listed every run).
- The smoke's `[smoke]` issue is kept. Its title is `wl-<scratch id> — [smoke] PR-less close`, it is closed `completed`, and the PR body names it. It stays as the close receipt: `thewolff-engineer` cannot delete issues, and the reconciler ignores closed issues it cannot map.
