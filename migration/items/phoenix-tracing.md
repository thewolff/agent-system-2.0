M7's "Phoenix receives the spans", wired. Workload `wl-mv65t5d34lts00` (normal stakes, plan revision 4 at `~/agent-scratch/agent-system-2.0/wl-mv65t5d34lts00/PLAN.md`: revision 3 approved by Jo, § 8 folds in Jo's 2026-10-14 rulings that Phoenix is self-hosted, on by default for fresh installs, and covers every OMP seat). The M7 row put the endpoint in the profile template, which cannot work: OMP reads `OTEL_*` from its environment once at startup (`initTelemetryExport` in OMP's `src/telemetry-export.ts`) and no OMP setting carries it. So as2 sets the env when it starts `omp`.

**The switch.** `observability.phoenix` in the installed profile's `config.yml`: `all` (the template value), `off`, or a list of `wl-…` ids, beside an `otel:` map of the `OTEL_*` names to export (traces to `http://127.0.0.1:6006/v1/traces` over `http/protobuf`; logs, metrics and message content `none`). One reader, `tracingEnv` in `surface/src/tracing.ts`. `surface/scripts/lane.ts` applies it after `laneEnv` at both lane spawn sites (the autonomous runner and `as2 lane <wl>`, through `laneSpawnEnv`); `bin/as2` applies it to the orchestrator (the default branch and `--print`, through `bun surface/scripts/tracing.ts env orchestrator`); Jo's seat launcher applies it to every other OMP seat (`env seat <name>`, see Seats). Off strips every inherited `OTEL_*` and sets `OTEL_SDK_DISABLED=true`, so no `.env` file OMP reads can turn it back on. On sets every name, plus `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` carrying `openinference.project.name` and the `as2.*` role attributes. Every name of the template map is required while on (`OTEL_REQUIRED`): one missing, empty or dropped turns tracing off, because OMP would fill it from a workload repo's `.env` (review r1). Phoenix 20.3.0 keeps only `openinference.project.name` of a span's resource (`get_project_name` in `phoenix/utilities/project.py`), so each workload's lane and hands land in Phoenix project `as2-<wl-id>`, the orchestrator in `as2-orchestrator` and a seat in `seat-<name>`; the `as2.*` attributes do not reach Phoenix. The orchestrator and the seats are on only under `all`. A missing or malformed block reads as off and never fails a launch. Hands run in their lane's process and inherit its env, so nothing is passed to them. The word is `as2 phoenix off|all|<wl-id>`; it prints the old and new value like `as2 on|off`. A re-install keeps the installed value (`install.sh` runs `tracing.ts carry`), so `as2 phoenix off` is the one off and survives `as2 install`; only a fresh profile starts at `all`. The setting is read at launch, so a flip reaches a running process only when it is relaunched.

**Phoenix.** A LaunchAgent, `com.agent-system-2.phoenix`, managed by `bash install/phoenix-agent.sh on|off|status`. `install.sh` (step 6e) runs `on` on macOS unless the switch is `off`, and only when `$HOME` is the user's own home directory as the user database (`dscl`) has it: launchd has one `gui/<uid>` domain per user, so an install into a test's temp HOME must not boot out the real job. `phoenix-agent.sh` refuses `on`/`off` from any other HOME with the real `launchctl` (exit 2), after an install test from a temp HOME stopped the running Phoenix on 2026-10-14 (Bun's `os.userInfo().homedir` follows `$HOME`, so the first check let it through). A failing `on` is reported with its retry command and does not fail the install. It serves on `127.0.0.1:6006` (UI and OTLP over HTTP) and `127.0.0.1:4317` (gRPC), with its data in `~/.agent-system-2/phoenix/data`, 30-day retention and Phoenix's own telemetry off. `on` waits up to 240 s for the job's own Phoenix to answer (cold starts measured 17 s and 83 s to bind; the wrapper's own bind deadline is 300 s). `off` boots it out and removes the plist; the data is kept and its `rm -r` is printed, not run.

**Seats.** Every OMP seat Jo starts outside as2 runs through Jo's seat launcher, which is in no repository: `~/.omp/agent/seat-launchers/launch-seat` (the foreground seat) and `seat-bin/omp` (every background seat) start `omp` through `env` with the words `bun <as2 checkout>/surface/scripts/tracing.ts env seat <name>` prints, the checkout being the one the `as2` link resolves to. Any failure there (no checkout, no bun, a reader without the word) starts the seat with `OTEL_SDK_DISABLED=true` and one stderr line, never a refused launch. Each edited file was first copied to `<file>.pre-phoenix-<UTC stamp>`.

**The gRPC loopback shim.** Phoenix 20.3.0's OTLP gRPC receiver binds `[::]` whatever `PHOENIX_HOST` says. `install/phoenix-serve.py` wraps `grpc.aio.server` so `add_insecure_port` and `add_secure_port` bind `127.0.0.1`. It refuses to start (exit 78) on any Phoenix version but 20.3.0, so an upgrade stops Phoenix until the pin is updated; OMP is unaffected. The wrapper launchd runs, `install/phoenix-run.sh`, checks the listeners every 10 s for the process's life and kills Phoenix (exit 78) on any address that is not `127.0.0.1`, and also when `lsof` can no longer see both loopback listeners: a check that cannot run never passes as clean. The same holds for the cap: a footprint sample that cannot be taken kills Phoenix (exit 78).

**The cap.** 1536 MiB of physical footprint (`PHOENIX_MEM_CAP_MB`). `phoenix-run.sh` tries the kernel limit first (`ulimit -v` and `ulimit -d`, outcome logged); macOS refused both, inside the fence and outside it (Jo's `phoenix-up.zsh`, 2026-10-13). It then samples Phoenix's footprint every 1 s with `install/phoenix-footprint.py` (`proc_pid_rusage`, `ri_phys_footprint`, run with Phoenix's Python, about 19 ms a sample) and SIGKILLs Phoenix on the first sample over (exit 75; launchd restarts it after 60 s). The footprint, not RSS: under memory pressure macOS compresses or swaps a process's pages, so RSS understates what it holds. Jo's 2026-10-14 runs had a fake Phoenix hold 3 GiB while no RSS sample passed 326 MiB, and a probe holding 768 MiB showed 124 MiB resident against a 792560 KiB footprint. The cap is therefore the watchdog: the footprint may pass 1536 MiB for up to one 1 s sample. Jo accepted that (plan tradeoff 1).

**Fault tolerance.** Export is a background batch that a turn never waits on. A send gives up after 2 s (`OTEL_EXPORTER_OTLP_TRACES_TIMEOUT=2000`) and the batch is dropped silently: OMP sets no `diag` logger, so nothing reaches the TUI or the lane log. The queue is bounded. OMP 18.8.6 does not wait for the exporter at exit (`omp --mode rpc` calls `process.exit` on stdin EOF and postmortem cleanup is fire-and-forget), so Phoenix down never delays an exit; the cost is that spans ending in an omp process's last ~5 s (the batch processor's schedule delay) are never sent. Measured against a stub model: median turn wall +2.2 ms with the endpoint refused, +0.6 ms against a black hole, no stderr lines, exit 17–31 ms after the last frame (`omp-cost/RESULT.md` beside the plan). Stopping Phoenix (`phoenix-agent.sh off`) is the instant off for running processes; `as2 phoenix off` is the off for the next launch.

**Rollout.** Merge, then `as2 install`: it keeps an installed switch value, starts Phoenix, and every lane, the orchestrator and every seat export from their next launch. A profile installed before this item has no `observability` block, so the carry finds nothing and it starts at `all`. To stop: `as2 phoenix off` (next launches), and `bash install/phoenix-agent.sh off` (Phoenix itself).

**Proof.** The cap: Jo's `rootcause-watchdog/repro.sh lane-fp` (2026-10-14, outside the fence, beside the plan) ran this wrapper at 1536 MiB against a process growing 64 MiB/s; the wrapper logged `memory cap: footprint sample 1580353 KiB > cap 1572864 KiB (1536 MiB)` and exited 75, where the RSS wrapper it replaces never fired. The seat launcher's test fails on the pre-Phoenix launcher and passes on the edited one (`watchdog-1536.log`, beside the plan). The live lane proof (spans in the UI, lanes unaffected with Phoenix killed) is `proof/live-proof.zsh` beside the plan, run outside the fence after `as2 install`.
