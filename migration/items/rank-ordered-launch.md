**Stacks on PR #153 (`migration/items/jev-ranking.md`) and merges after it.** Workload `wl-mv8wzytml878b4` (plan rev 5 at `/Users/jowolff/agent-scratch/agent-system-2.0/wl-mv8wzytml878b4/PLAN.md`, § 1 and § 2 D1–D4). Its branch is cut from PR #153's branch and uses #153's `rankOpen`, `as2_rank` and launch gate unchanged in shape. It makes the rank the launch order by default and adds priority pause, which #153 does not have.

**What changed.**
- Launch follows the rank by default. `DEFAULT_RANK_CONFIG.mode` (`surface/src/rank-launch.ts`) and `jevRank.mode` in `profile/config.yml` are now `order`, and a missing or malformed value reads `order`. So the drain walks the rank, and the open tool and the wake tick refuse a lower-ranked workload with `ranked: below <wl>` while a higher one can launch. A freed slot goes to the top-ranked launchable workload, not the oldest. Jo's launch word (`launch-requested:`) and `as2 lane` are still never held. `as2 rank-mode show` turns it back to oldest-first.
- Jo's ruled list. "A, then B, then C" is one `as2_rank { first: [A, B, C], inputId }` call (`surface/extensions/rank.ts`). In one transaction it writes one `rank-override: <wl> input <in-id> shown <id> pos <k>` per item and a `rank-unpin:` for every standing pin not in the list, and spends the input once. Jo's new list replaces the previous ruling. `rankOpen` (`surface/src/rank.ts`) puts ruled items first by position, then the Jev order, then unscored items oldest first. An older single `first` with no `pos` keeps #153's newest-pin-first rule and sits above every older ruling.
- Priority pause, only on Jo's ruling and only in `order` mode. When the lane cap is full and a workload Jo ruled is waiting (autonomous, not running, launchable apart from the cap), `preemptFor` (`surface/src/rank-launch.ts`) writes one `lane-stop: <L> requested priority-for-<X> by rank` on the lowest-ranked running autonomous workload below X. That workload must have a ready lane and no pending stop. It is never an interactive lane and never a workload ruled at or above X. Three places call it: `triggerLaunch` when the gate answers `cap` (`surface/extensions/launch.ts`), the wake tick (`surface/extensions/wake.ts`), and `as2_rank` after a `first` ruling. The runner takes it through the existing stop path (exit intended, no `lane-died:`, `lane-exit: … outcome stop reason priority-for-<X>`). The drain then gives the freed slot to the top-ranked launchable workload. A stop already requested counts as a slot on its way, so a repeated tick writes nothing more. There is no new control prefix.
- States, from rows the stop path already writes (`priorityPausingOf` and `priorityPausedOf` in `surface/src/launch.ts`). While the stop is pending the workload is priority-pausing. After the accepted priority stop and its exit, with no launch attempt since, it is priority-paused. A ceiling stop, Jo's `as2 lane stop` and a death are neither.
- Self-relaunch. `launchable` gains the cause `priority <exitId>`, checked after `resume`. The gate admits it only when nothing ranked above it can launch, so the paused workload relaunches by itself, resuming its newest session, when a slot comes back to it. Any launch attempt on the workload ends the state, so a second automatic launch cannot happen.
- What Jo sees. Each ranked workload line in the wake render (`surface/src/render.ts`) and in the `as2_rank` table / `as2 rank` carries `rank #n`, marked `ruled` for Jo's items. Scheduled `due:` rows and the standing row carry no rank. A paused workload shows `priority-pausing for <X>`, then `priority-paused for <X> (relaunches when a slot reaches it)` beside `lane: none`. Neither is a needs-you line. `triggerLaunch` and the tick print `priority-pausing <L> on <wl> for <X>` when they write a stop.
