**Built on branch `wl/wl-mvfjen3q5mqi2o`, PR #250.** Workload `wl-mvfjen3q5mqi2o` (normal stakes, plan at `~/agent-scratch/agent-system-2.0/wl-mvfjen3q5mqi2o/PLAN.md`, approved by Jo). Closes issue #223. It changes item 24's close freshness check (`closeFreshness`, `surface/src/test-run.ts`; the close set in `surface/src/close-entry.ts`).

**Evidence.** Two finished workloads could not close, and the refusal told each to do something that cannot work. (1) Issue #223: the merge train `wl-mva2bas9070hkw` wrote a `push-dest:` for `wl/wl-mv8s8srodefytc`, so its close set picked up #156 and #220, another workload's PRs merged hours before the train pushed. The close refused with `PR #156 has no test-run result: call lane_full_test`, and the runner refuses merged PRs. (2) The bindfix workload `wl-mv5qdfvv82ivwg`: PR #104 merged at 393797a, a later merge of origin/main (merge commit c5585a6). The lane's last green was 4a1c9ce. The close refused with `PR #104's head 393797a is not the green 4a1c9ce: commit 393797a is a merge; call lane_full_test`. Running the suite at the old merge commit is no way out either: the runner's preflight refuses a tree whose test-exec bundle inputs differ from the installed bundle.

**The fix.** (D1) A PR found only through a `push-dest:` branch other than `wl/<wl>` joins the close set only when its head contains a sha this workload's holders pushed to that branch. The remote name is ignored, as `boundBranches` ignores it. Containment is `git merge-base --is-ancestor`, and only an answered result decides; a shallow clone refuses the close. Every PR from `wl/<wl>` stays in the set. The runner still admits any PR on a push-dest branch; only the close set narrows. (D2) A merged PR that no green of this workload covers passes on a `test-run: … green` written by the test runner on any workload, when the run's sha is on this repository's freshly fetched default branch and is the PR's merged head (or reaches it through decision-log-only commits) or contains the PR's merge commit. (D3) Jo's surface word `waive-pr <wl-…> <N> [<N> …]` passes a merged PR nothing covers. It is built like `test-pr`: Jo's instruction `waive-pr <wl> <N…>` and the surface's `waive-pr: <N…> <instruction id>` in one transaction, read by `waivedPrs` in `surface/src/launch.ts`, and `waive-pr:` is a surface-only control prefix. A waiver never passes an open PR, never covers the candidate's code delta, and never admits a test run. The close's why line names it: `waived by Jo: #N (in-…)`. (D4) For a merged PR with no qualifying result, the refusal names the merge commit and the two ways through (a green run on the default branch that contains it, or `waive-pr`) instead of `call lane_full_test`. Open PRs, closed PRs, red-main train PRs and the candidate code-delta rule are unchanged.

**Tradeoffs.** D2 trusts any runner green on this repository's main line that contains the merge commit. That is an integration snapshot, not proof the PR's lines still run: a PR reverted before the run is covered by main without it. Repository identity is git evidence (the run's sha on this origin's default branch), not a field the run records, so a fork sharing history and served under another command could be misattributed; one repository is served today. A runner mode that runs the suite on main was not built: it would change the runner and its installed bundle and need a reinstall, and running at an old merge commit hits preflight input drift. The covering green of D2 gives the same evidence once any later PR that merges main in goes green and merges.

**Tests:** `surface/test/close-fresh.test.ts` (the #223 shape, the covering green on main, the revert policy, the waiver, the new refusal, open PRs unchanged), `surface/test/input.test.ts` (the word) and `surface/test/launch.test.ts` (`waivedPrs`, forged entries bind nothing).
