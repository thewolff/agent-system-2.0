In the plan's read of the live ledger on 2026-10-13 (PLAN § "The figure, re-derived"), none of the 8 round-limit questions and none of the 6 ceiling questions named a file, so Jo answered them without the plan, the verdicts or the PR in front of them.

**What:** a question is *linked* when one of its options is `approve`, `accept` or `extend` (any case). Machinery computes its links from the ledger when it is raised (`linksAtRaise` and `expectedLinks` in `surface/src/question-links.ts`); a model never chooses them. They are recorded in the same write as the question, as a `question-links: <q-id> <json>` control entry (the newest entry wins). The header lines, in order:

- `plan: <path>`: the newest `plan-file:` entry, else line 1 of the workload's newest plan question. The classifier records `plan-file:` from the `plan file: <absolute path>` line that a plan-slice review brief must now carry, and refuses the brief without that line. The line reads `plan: none — <wl> is not plan-first: it has no plan slice` only when the workload never was plan-first.
- `review: <path>`: one line per member of the newest *complete* review round of the question's slice. A round is complete when every member has settled. Every review loop counts, so the plan question links the verdicts of the loop that passed. When the question's slice has no round, the question links the newest complete round of every reviewed slice instead, one line per member, labelled `review (sl-…, round n): <path>`. An orchestrator relay always falls in this case, because it sits on the standing slice. Nothing is picked, so no other slice's verdict can stand in for the relevant one. Each member's verdict file is `<ledger dir>/reviews/<wl>/<token>.md`, named by a `review-verdict:` entry. The classifier writes it at settle; a member that never replied gets its diagnostic there instead. A round that settled before this change gets its files on first need: `materializeVerdicts` builds them from the round's `review-round:` entries, adding the hand's own reply when one exists. The line reads `review: none — no review round has completed on <wl>` only when no round has.
- `pr: <url>`: one line per open PR of `wl/<wl>` (from `gh pr list --head wl/<wl> --state open`), plus every PR the ledger records. `pr-seen:` is written by each successful read and after an exit-0 `gh pr create` in a lane's bash or in close-entry; `test-requested:` entries count too.

**Refusals:** `lane_raise_question` and `orchestrator_raise_question` refuse a linked question whose body does not start with exactly these lines (`linkProblem`). The refusal names the missing or wrong line and prints the header to paste; nothing is asked. A linked orchestrator question must also name `about`. The plan question keeps its D7 shape, and PR #111's `planQuestionProblem` is unchanged. Once that check passes, `planLinkProblem` checks two more things: line 1 must be the recorded plan file, and the `review:` line's verdict file must be one of the plan slice's newest-round files. A plan-first workload with no recorded plan file is refused ("record the plan file: dispatch the plan review with a `plan file:` line"); it never passes as `none`.

**Plan approval wait:** after the D7 shape check, a plan approve question is refused unless the plan slice's latest review round has completed with authoritative verdict links, even when an older round completed. A pending fan-out says how many members have settled (`n of m`) and to wait for all members and retry; no question is written. The review file named in the body must still match the latest round. Older open plan-first workloads with no completed review-round metadata are not grandfathered in.

**PR read failure: fallback for machinery, refusal for models.** When `gh pr list` fails, a model-authored question is refused with the error and "retry once gh answers". Machinery questions never wait on the network, because they guard the review loop and the budget. These are the round-limit question (`roundLimitQuestionBody`) and the 80 % ceiling question (`ceilingQuestionBody`); both require links and throw if their header is missing. They carry every recorded PR plus `pr: unverified — gh pr list failed: <reason>`. On a plan-first workload with no recorded plan they show `plan: missing — <reason>` instead of being refused. The surface's tick re-reads the PRs of every open linked question: every tick while one is unverified, at most every 10 minutes otherwise. It records a new `question-links:` entry when the set changes. Questions already open when this ships get their first entry from the same tick, and until then the display computes their links in memory.

**Display:** the needs-you and wake lines show a linked question's links first, one per line and uncut, read from its newest `question-links:` entry. The plan question keeps PR #112's layout: the bare plan path stays directly beneath the q- id, the `review:` and `pr:` lines follow, then body lines 2..n. That ordering is the one deliberate change to #112's test 7a; `withPlanPaths` is unchanged. OSC 8 is applied at display only. A message renderer for the surface's displayed messages (`surface-needs-you`, `surface-wake`, `surface-notices`, `surface-plan-path`) renders each link line as a plain text row and wraps its absolute path or URL with OMP's `fileHyperlink` / `uriHyperlink`, so the target shows once. OMP's policy decides whether hyperlinks are on (they are inside HerdR). When they are off, for example with `PI_NO_HYPERLINKS=1`, the row shows the plain absolute path. Message content, which is what Ilex reads, and every ledger body stay plain text with no escape byte.

**Tradeoffs (stated in the plan):** a PR that no lane recorded while `gh` cannot be reached shows as `pr: unverified`, not as its URL. Raising a model-authored linked question needs `gh` and the network. A plan-slice review dispatched without a `plan file:` line is refused, once per lane that has not yet seen the refusal. **Tests:** one per question kind, in `classifier/test/question-links.test.ts`, `surface/test/question-links.test.ts` and `surface/test/question-links-render.test.ts`. The real-lane check in a HerdR pane is the workload's acceptance slice, answered pass or fail by Jo.
