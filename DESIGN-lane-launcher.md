# Lane launcher — design

Status: ruled 2026-09-30 (Jo: Q1/Q2 per Plumb's recommendation); gaslighted twice, every critique taken (§ 10); build not started.

Scope: how an open workload gets a live lane session, how that session is configured, how it lives and dies, and how the orchestrator (Ilex) and Jo see it. Written from the three-lab quorum synthesis (`~/agent-scratch/agent-system-2.0/migration/M7/lane-launcher/SYNTHESIS.md`) under Jo's two rulings. Nothing here is built; pseudocode is illustrative. Every code fact carries a repo-relative `file:line` and a quoted anchor so the reference survives edits; OMP facts cite the installed 18.4.4 source under `@oh-my-pi/pi-coding-agent/src/`.

**QUESTION — ledger schema v6 or not.** The holder-checked release (decision 5) can be enforced at two levels. *File level* (a trigger beside `workloads_holder_no_steal`, `ledger/schema.sql:416`, plus typed launch rows) is schema version 6 — and the module has no upgrade path: a file at an older version "is refused unchanged: move it aside and install a new ledger" (`ledger/src/index.ts:31-33`, `LedgerSchemaVersionError`). Jo's live ledger holds the standing workload and the two real M7 workloads, so v6 costs a reinstall plus a by-hand copy of those rows. *Module level* (`releaseWorkload` gains a required `holder` and a `WHERE holder = ?`; launch facts stay prefixed `assumption` entries like `repo:` and `artifact-command:` today) is schema-neutral and covers the threat model — accidental misuse by the system's own lanes (SPEC § A4), whose raw writes P-11 row 10 and the OS fence already refuse. Recommendation: **module level now, no v6**; the trigger text is written below and waits for the next natural schema bump. The page proceeds on that recommendation; every line that changes under v6 says so.

## 2. Decisions

Each decision names the fork it closes (A–L in SYNTHESIS.md § 2) and the lab whose shape it takes. Rulings first, then the transfer list.

1. **Who starts a lane — fork A, Claude's shape plus Kimi's predicate (Jo's ruling Q1).** At `orchestrator_open_workload`, after the row and the `repo:` entry are written (`surface/extensions/workload.ts:70-71`, `ledger.openWorkload(…)` then `recordRepo(ledger, id, repo)`), the surface extension evaluates one pure launch predicate and, when it says launch, execs the lane starter (`surface/scripts/lane.ts launch`) through the extension API (`pi.exec`, `extensibility/extensions/types.ts:1578`, "Execute a shell command") — not through the bash tool, so P-11 row 15 never sees it. The same predicate runs again on the existing 60-second poll (`surface/extensions/wake.ts:124`, `timer(() => poll(s), s.pollMs)`; `POLL_MS = 60_000`, `surface/src/types.ts:74`) as catch-up: a crash between open and spawn, or an orchestrator that was not running at open, is repaired within a minute by the same function. There is no separate supervisor process (Codex's shape is not taken: a second long-lived process whose own liveness must be recorded and watched). The predicate excludes the standing workload, `due:` rows (`DUE_PREFIX` briefs written by `orchestrator_schedule`, `surface/extensions/workload.ts:137`), and user-driven workloads (§ B13.1 "mode = who is steering"): those two never auto-launch, and the open tool's result carries the by-hand command instead (decision 14).

2. **What an autonomous lane process is — fork B and fork C, Claude's shape (Jo's ruling Q2).** One `omp --mode rpc --no-ui …` process per lane, started in the worktree, given exactly one `prompt` frame (`modes/rpc/rpc-types.ts:29`, `type: "prompt"`), and waited on for its one `prompt_result` (`modes/rpc/rpc-prompt-results.ts:145-148`, `type: "prompt_result"`, `status: outcome.status`; statuses `"completed" | "aborted" | "error"`, `rpc-types.ts:149`). A small **detached per-lane runner** (Bun script, its own session, not a child of the orchestrator's process tree) holds stdin/stdout, writes the log, and on any exit of `omp` — clean, error, deadline, or SIGKILL — releases the workload if the holder is still this lane, within seconds. Exit is typed: the runner closes stdin after `prompt_result`, and stdin EOF makes OMP drain, dispose the session (which "also emits `session_shutdown`", `modes/rpc/rpc-mode.ts:1725`) and exit 0 (`rpc-mode.ts:1760-1774`, "stdin closed — RPC client is gone … return disposeAndExit()"), so the existing lane row's shutdown handler (`surface/extensions/lane.ts:127-144`, `pi.on("session_shutdown", …)` … `ledger.releaseWorkload(w.id, …)`) runs on the clean path and the runner is the belt-and-braces for the unclean one. The same path covers the runner's own death: the runner holds the only write end of `omp`'s stdin, so when it dies the pipe closes and `omp` releases at the end of its in-flight prompt (§ 6). Not adopted: persistent turn-by-turn rpc driven from ledger state (Codex), and print mode `-p` (Kimi: no typed exit, nothing can abort it). `--no-ui` is legal only with `--mode rpc` (`main.ts:250-254`, "`--no-ui` requires `--mode rpc`").

3. **Where a lane works — synthesis "Needs you" item 1 and fork K, Claude's alternate.** The OS fence's first deny target is the ledger *directory*: `fenceTargets` opens with `{ kind: "subpath", path: canonical(dirname(ledgerPath), "the ledger directory") }` (`gates/src/fence.ts:201`) and the default ledger path is `$HOME/.agent-system-2/ledger.db` (`ledger/src/locality.ts:14-18`, `defaultLedgerPath`). Every bash call a lane makes runs under that Seatbelt profile (`fence.ts:229-231`, `(deny file-write* (subpath …))`), so a worktree anywhere under `~/.agent-system-2/` cannot be committed to, built in, or tested in. Worktrees therefore live **beside the checkout**: `<parent>/<repo-basename>-lanes/<workload-id>/` (for this repo, `/Users/jowolff/code/agent-system-2.0-lanes/wl-…/`), on branch `wl/<workload-id>` cut from the remote's default branch when an `origin` exists, else from the local default. Inside the repo (`<repo>/.worktrees/`) was checked and rejected: the fence would allow it — for a directory inside a repository the fence denies only the `.git` entry itself (`fence.ts:175`, `out.push({ kind: "literal", path: dotGit })`) and the common `hooks` directory (`fence.ts:185`) — but the brief's install rule says state "never enters the repo", and an untracked directory inside the checkout is state in the repo. Cleanup is an explicit `as2 lane cleanup <workload>` (Claude and Codex), refused while the worktree is dirty or its branch has commits not on the remote; the branch is never deleted (reserved, § A4). The close tool does not touch worktrees (Plumb's draft had it remove them at close; no lab put cleanup there). Relaunch reuses an existing branch and worktree: `git worktree add <path> wl/<wl>` without `-b` when the branch exists, and nothing when the worktree is already registered (Codex's attack on Kimi's unconditional `-b`).

4. **How a lane writes the ledger — fork E, Codex's shape.** No registered tool today adds or completes a slice, raises a question, enqueues a message, or releases: the by-hand script did all of it through the module from outside OMP (`~/agent-scratch/agent-system-2.0/migration/M7/lane-by-hand/wl-munn32rmt6ajnk.ts`, `ledger.addSlice`, `completeSlice`, `enqueue`, `releaseWorkload`). A bash CLI cannot do it from inside a lane: the fence denies the SQLite write at the OS level and has no script exemption (Claude's attack on Kimi). The lane gets **extension tools**, registered in the surface's own extension the way `slice_artifact` is (`surface/extensions/lane.ts:81-107`, `pi.registerTool({ name: ARTIFACT_TOOL, loadMode: "essential", …`), `loadMode: "essential"` so they are top-level and not `xd://` devices (M7 finding 1). Exact list and inputs in § 4. Every one validates ownership before writing: the session is a bound lane, the workload is this lane's, the holder is this lane with a live lease, and a named slice belongs to the workload. The tools that take a free body (`lane_record_entry`, `lane_message`, `lane_raise_question`) refuse one that starts with a reserved control prefix (§ 5): lifecycle entries are machinery writes, and a lane note shaped like one is refused, never interpreted. Two tools end the lane's hold, and both are terminal for the session (§ 4): `lane_release`, and `lane_handoff`, § B5's "I've got X", which transfers the workload to Jo (`SPEC-2.0.md:484-487`, "hands the workload to Jo … the workload stays open with `lane = Jo`").

5. **Holder-checked release — fork D, Codex's shape at module level (see the QUESTION above).** `releaseWorkload` today updates `WHERE id = ?` with no holder condition (`ledger/src/index.ts:471-476`, `UPDATE workloads SET holder = NULL, holder_lease_until = NULL … WHERE id = ? RETURNING id`), so a stale lane can release a live one. It becomes `releaseWorkload(id, { by, holder })` with `AND holder = ?` in the predicate; zero rows is a typed refusal (`not the holder`), not `expectOne`'s generic error. Identity has three parts, Codex's shape: the **lane id** `lane-<workload-suffix>-<n>`, where `n` is minted inside the same `BEGIN IMMEDIATE` transaction as the cap check and the pre-claim (`ledger/src/index.ts:428-431`, `write<T>(fn)` "Run `fn` in BEGIN IMMEDIATE") so two concurrent starts cannot mint the same ordinal (Codex's attack on Claude); the **PID** and the **process start time** of `omp`, recorded by the runner in a `lane-started:` entry. The lane id is what the ledger checks. The runner signals `omp` only through its own child handle (`child.kill()`), before the child's exit event, so it never needs the PID; PID and start time are what `as2 lane stop` re-reads before signalling an `omp` whose runner is gone, so a reused PID is never killed.

6. **Mode flip on a running lane — fork J, Codex's shape.** Jo's one-word flip lands as today (`flipMode`, `ledger/src/index.ts:485-497`, "the mode-flip instruction and the flip land in one transaction"). For a running autonomous lane the surface then writes a `lane-stop:` request naming the reason `mode-flip`; the runner sees it on its ledger poll, persists its acceptance (`lane-stop: <laneId> accepted <request entry id>`) before it sends `abort` (`rpc-types.ts:33`, `type: "abort"`), closes stdin, and records `lane-exit: … outcome stop reason mode-flip` with the real exit code and signal. No `lane-died:` comes from the runner or from the lane row's shutdown handler, even with a slice open or paused, since the exit was requested (the exit classification, decision 14). A starter already on its way when the flip lands is refused `user-driven` inside `reserveLane` (decision 8). The open tool's result and the wake render then carry the by-hand command `as2 lane <workload>`, which relaunches **interactively** with `--resume <session path>` on the same worktree and binding. The reverse flip (user-driven → autonomous) is Jo leaving the interactive session and saying the word; the surface writes `launch-requested: by jo (mode-flip)` in the same transaction as the flip, so the predicate (decision 7: a request no attempt has consumed) launches an autonomous lane with `--resume <recorded session>` — no separate `orchestrator_launch_lane` call. **Plumb's draft's `steer` over the held pipe is not adopted**: a one-prompt rpc lane has no second prompt to steer into, and the labs' shape (stop at a boundary, relaunch in the other mode) needs no pipe kept open across the flip.

7. **Never auto-restart — fork F, Claude and Codex.** A lane that dies writes (or has written for it) a `lane-died:` message; the surface pushes it to Jo (decision 9); Jo, or Ilex on Jo's word, relaunches with `orchestrator_launch_lane`. Kimi's one automatic retry is not taken: it relaunched a finished-but-unclosed workload (Claude's attack) and could not recreate a worktree it had already made (Codex's attack). The launch predicate encodes this with causes, not timestamps: every autonomous launch consumes exactly one cause, named in its `launch:` entry — `first` (the workload has no `launch:` yet), `request <entry id>` (a `launch-requested:` entry), or `resume <instruction ids>` (resolutions of questions a launched lane raised, decision 14) — and a cause that some `launch:` already names is never used again. A death supplies no new cause, so a workload that has had an attempt launches again only on Jo's word or on a resolution. A launch attempt is a `launch:` entry, and only `reserveLane` writes one, in the transaction that mints the lane id and consumes the cause (decision 8); a refusal of any kind writes nothing.

8. **Global cap 3, atomic — fork G, Claude's number with Codex's atomicity.** At most three autonomous lanes hold workloads at once (`AGENT_SYSTEM_MAX_LANES`, default 3). Eligibility, count and claim are one ledger transaction: a new module method `reserveLane(workloadId, { by, cap, leaseMs, interactive? })` runs, inside one `write()` (BEGIN IMMEDIATE, `ledger/src/index.ts:429-431`), the launch predicate again against rows it reads there — the workload row (status, mode, brief, holder, lease), its control entries, its resolutions, and the live-lane count (open autonomous workloads whose holder matches `lane-*` and whose lease is null or not yet expired) — then the ordinal mint, the pre-claim (the `claimWorkload` update with `by: "lane-starter"`, `holder: laneId`, a 3-minute lease), and the attempt entry `launch: <laneId> cause <cause> requested-by <who>` (an `assumption` entry, `by: "lane-starter"`), which consumes the one cause the predicate returned (decision 7); it returns `{ ok: true, laneId, cause }` or `{ ok: false, reason }` with the predicate's reason. The surface's own run of the predicate only decides whether to exec the starter; the run inside the transaction is the one that binds, so whatever lands between the two is seen: a flip to user-driven refuses `user-driven`, and a second starter arriving after the first reserved, failed and released finds the cause already named and refuses `died-not-relaunched`. A refusal returns before any write: no `launch:`, no `launch-failed:`, no message, so a refused workload's predicate inputs are unchanged and the tick launches it once the reason clears. `launch-failed:` is written only for a failure after a reservation (decision 9). **Interactive reservation** (`lane.ts interactive`, the by-hand `as2 lane <wl>`) goes through the same method with `interactive: true` and its own policy: allowed on an open workload, not the standing one, brief not `due:`, mode user-driven, holder null or lease lapsed; refused on an autonomous workload (the result names the flip word) and while an autonomous lane holds it (names the lane, suggests `as2 lane stop`). The cap and the cause rules do not apply, since Jo's command is the authority; the attempt is written with cause `interactive`, which consumes nothing. The stamp is `"lane-starter"`, never the lane id, because `claimWorkload` sets `changed_by` from `by` on every winning update (`ledger/src/index.ts:458`, `UPDATE workloads SET holder = ?, holder_lease_until = ?, changed_by = ? …`) and the lane row's own claim stamps the lane id (`surface/extensions/lane.ts:74`, `ledger.claimWorkload(w.id, { by: s.laneId, holder: s.laneId, …`): the workload's `changed_by` becomes the lane id only when the lane's extension has loaded and bound, which is what readiness (decision 14) observes. SQLite's write lock serializes writers across processes, so a fourth concurrent start sees three and refuses (the sequential "refuses the fourth" test that Codex called insufficient is replaced by a concurrent one, § 8). The pre-claim's three-minute lease is the launch readiness window (decision 14).

9. **Launch failure rides `lane-died:` — fork I, Claude's shape.** Between wakes, the poll delivers only § B3 error lines (`surface/extensions/wake.ts:26-31`, `readLines` → `errorLines`), and among lane-to-orchestrator messages only three body prefixes ever become lines: `lane-died:` (source 4, `surface/src/errors.ts:19-20`), `prompt-wait:` (source 5, `errors.ts:21-22`) and `artifact-failed:` (source 3). Any other message to the orchestrator is consumed at the next read, never pushed (`surface/src/delivery.ts:64-66`, `advanceMessage(id, "delivered", …)`). So a launch failure after a reservation writes a `launch-failed:` entry **and** a message `lane-died: <laneId>: launch failed at <stage>: <reason>` — the body shape `laneDeaths` parses (`surface/src/signals.ts:48`, `/^lane-died:\s*(\S+?):\s/`) — and Jo sees it within one poll. When the launch is synchronous with a tool call (open, or `orchestrator_launch_lane`) the tool result carries the same line too. Codex's workload-level `question` rows would need `raiseQuestion` to accept a null `sliceId` (`ledger/src/index.ts:596`, `sliceId: string`) and a schema change; not taken.

10. **Lanes survive `as2` exiting — fork C, all three labs against Plumb's draft.** The runner is detached from the orchestrator's process (its own session; stdio to its log, never to the orchestrator's pipes), so closing the orchestrator terminal, `/exit`, or a crash of `as2` leaves every lane running. The orchestrator on relaunch reads the ledger (wake, § B7) and finds the live holders; nothing is resumed or aborted on its behalf. Plumb's draft had lanes as children that get `abort` on exit and resume on the next open; unanimous against.

11. **Converged bundle — no fork, and fork L (Claude and Kimi: no gates edits).** Worktree-per-workload on its own branch, never in the checkout (decision 3). Per-lane `--session-dir` — `~/.agent-system-2/lanes/<workload-id>/sessions` — never `--no-session`: with `--session-dir` and no `--resume`, OMP creates the new session there (`main.ts:1232-1235`, "If --session-dir provided without --continue/--resume, create new session there"); `--resume <path>` with a `/` or `.jsonl` in it opens exactly that file (`main.ts:1186-1187`). Binding by the three env vars (`gates/src/types.ts:25-27`, `ROLE_ENV = "AGENT_SYSTEM_ROLE"`, `WORKLOAD_ENV`, `LANE_ENV`) with the inherited `AGENT_SYSTEM_ROLE=orchestrator` — which `as2` sets (`bin/as2:85`, `exec env OMP_PROFILE="$PROFILE_NAME" AGENT_SYSTEM_ROLE=orchestrator omp --cwd "$REPO"`) and the starter would inherit — **overwritten to `lane`**, since the gates read role as orchestrator whenever that variable says so (`gates/src/session.ts:83-85`, `roleOf`). The lane commits on `wl/<wl>`, brings the remote default in by rebase or merge (row 8's upstream when the branch tracks nothing, `upstreams` in `gates/src/rows/r08-push-rebase.ts`), runs its declared test artifact on the final tree (row 8's evidence since 2026-10-01, MIGRATION.md § M7 follow-ups item 13), pushes with `-u`, and opens the PR. What happens to the PR is completion policy, which the launcher does not change: this machinery repo lands by Jo integrating (Jo's ruling), so a lane here never merges; a product repo follows the existing stakes-governed merge policy (`SPEC-2.0.md:456-460`: normal stakes, "merge proceeds on pass" of a judge slice and Jo is "told in one line after the merge"; production, a judge slice "then Jo", who "approves the merge"), and a merge of an approved, green PR is not a reserved action (`SPEC-2.0.md:233-234`, "merges of approved, green PRs (P-8d: no per-unit approval)"). The decision-log context the open tool already renders (`surface/extensions/workload.ts:73`, `decisionLogContext(logDir(repo), { since })`) reaches the lane inside the launch prompt, a real pipe, not a file the lane is hoped to read. A fake `omp` shim on PATH for unit tests and a chaos smoke are in the build (§ 8). The gates are not edited: Codex's rewrite of row 7 into a pre-execution readiness gate is out of scope per the quorum brief; readiness is the runner's concern (decision 14).

12. **`--max-time` and the ceiling — fork H, Kimi's env with Codex's ceiling tie.** `--max-time` is OMP's only hard cap: it sets one deadline from process start (`main.ts:1299-1300`, `options.deadline = Date.now() + parsed.maxTime * 1000`) and the agent loop ends its stream once passed (`@oh-my-pi/pi-agent-core/src/agent-loop.ts:1095-1096`, `isDeadlineExceeded`; the deadline timer aborts the loop, `:1179-1191`). No token cap exists and none is claimed. Default **2 h**, env `AGENT_SYSTEM_LANE_MAX_TIME` (a duration OMP parses: "5s", "10m", "1h", `cli/flag-tables.ts:88-104`). Claude's attack on Codex — the deadline ends the loop, not the process, so a persistent lane keeps renewing its lease — does not apply here: the loop ending produces the `prompt_result`, the runner closes stdin, the process exits. Once the workload ceiling exists (not built: MIGRATION.md M7 row, "**the workload ceiling is not built**"), a lane's cap and each hand's ceiling-share derive from the workload's *remaining* ceiling with the lane's own tokens counted (Codex); until then the fixed default stands and row 5's numeric check is not budget enforcement. This page states the dependency and designs nothing of the ceiling.

    *Amended 2026-09-30 by the workload ceiling (`DESIGN-workload-ceiling.md`, workload `wl-muolz8qtp6ylfk`):* `--max-time` is now the wall half of the workload's ceiling. With `AGENT_SYSTEM_LANE_MAX_TIME` unset, the runner passes the ceiling's remaining wall + 10 min. The runner's own meter stops the lane at 100 % first (`lane-stop: <lane> accepted ceiling`, outcome `stop`, no `lane-died:`), so the deadline is only a backstop. A commit that fails (no identity, a merge in progress) does not block the close; the tool result names the untracked path and the reason. Part of this build round.

14. **Unique ideas adopted.** *Parked on a question is not dead* (Claude): a lane whose prompt ends with a question it raised still open is **parked**. The park decision and the question read are one transaction: on `prompt_result` the runner calls `parkLane` (§ 5), which reads the questions whose `created_by` is this lane id (`ledger/schema.sql:133`) and, when any is open or resolved by a resolution no `launch:` has consumed, writes `lane-parked: <laneId> questions <qids> session <path>` in the same `write()`. The runner's outcome is `parked` when one is still open, and `resume-pending` when Jo resolved every one while the lane was winding down. Either way the runner then closes stdin and `omp` takes the same EOF path as a clean finish (decision 2): `session_shutdown`, release, no `lane-died:`. A slice pauses only on an open question (`ledger/schema.sql:441`, `slices_pause_needs_question`), and the question is already a § B3 item 5 line (`surface/src/errors.ts:21-22`, source 5, "every open `question`"). A parked lane holds no process and no cap slot. *Resume on a resolution, not a timestamp*: Jo resolves a question with the `answer` instruction the surface already writes (`surface/src/input.ts:77-78`, `ledger.answerQuestion(cmd.questionId, …)`) or with a withdrawal (`input.ts:83-84`, `ledger.withdrawQuestion(cmd.questionId, { …, then: cmd.then })`), and the schema settles the slice in the same statement: open again after an answer or a `replan` withdrawal, cancelled after a `cancel` (`ledger/schema.sql:526-544`, `questions_resolution_settles_slice`). A **resolution**, for the predicate, is an `answer` or `replan` instruction on a question a launched lane raised, whose slice it left `open`, and whose instruction id no `launch:` names. The next attempt consumes every outstanding one as its cause `resume <instruction ids>` and relaunches with `--resume <session path>` from the raising lane's `lane-started:`. Cancellation is never approval: a `cancel` withdrawal is not a resolution and relaunches nothing (Jo's word through `orchestrator_launch_lane` still can). The order of arrival stops mattering: an answer before the park is a `resume-pending` exit; an answer after the park but before `omp` released meets `held` on the synchronous trigger, and the tick launches once the holder is released, because the resolution is still unconsumed; a `replan` withdrawal follows the same path as an answer. The surface's answer and withdrawal paths run the trigger synchronously, so the relaunch does not wait for the next poll when the holder is already gone. The relaunched lane's first prompt carries the resolution text and instruction id, so the round trip of § B3 item 5 completes inside the lane's own conversation. One premise is read, not run, and three paths ride on it — the resolution relaunch, the mode-flip relaunch (decision 6), and a relaunch after a death: that `omp --mode rpc --resume <path>` continues the recorded conversation for a new `prompt` frame. What is read is only that `--resume <path>` opens exactly that file (`main.ts:1186-1187`). ## 3. Process shape

The launch path from open to release, then the catch-up path. `Ilex` is the orchestrator session; `surface` is its extension process; `starter` is `surface/scripts/lane.ts launch`, the short-lived process the extension execs; `runner` is `lane.ts run`, the detached per-lane process the starter spawns (one script, two processes); `omp` is the lane session; `ledger` is the SQLite file.

```mermaid
sequenceDiagram

    participant Ilex as Ilex (orchestrator)
    participant Surface as surface extension
    participant Ledger as ledger
    participant Starter as lane.ts launch (pi.exec)

    participant Omp as omp --mode rpc --no-ui (lane)
```

Catch-up path (the same predicate on the 60-second tick, `surface/extensions/wake.ts:103-124`, `const poll = …` / `timer(() => poll(s), s.pollMs)`): each poll, after `readLines`, the surface evaluates `launchable` for every open workload and execs the starter for each that qualifies, at most one per poll per workload. What it repairs: a crash between `openWorkload` and `pi.exec`; an orchestrator that was down when Jo relaunched with `orchestrator_launch_lane` from another session; a workload refused at the cap (the refusal wrote nothing, so the predicate still says launch once a slot frees); a parked lane resolved (answered, or withdrawn with replan) before its `omp` had finished releasing — the synchronous trigger on the answer path saw `held`, and the resolution is still unconsumed. What it leaves alone: a starter that reserved and then died before spawning the runner — its `launch:` was written in the reservation transaction and consumed its cause, so the predicate returns `died-not-relaunched`; the pre-claim lapses after three minutes, the lapse is recorded as `lane-died:` by `recordLapsedLeases` (`wake.ts:29`), and the workload is *not* relaunched (decision 7) until Jo says so. What it never does: relaunch after a death, launch a `due:` or user-driven workload, or exceed the cap.

Drain path (*amended 2026-10-09, MIGRATION.md item 71*): a lane slot freeing is a second trigger, so a queued launch no longer waits for an orchestrator session to be open. The runner's finalization spawns `lane.ts drain <wl>` detached and unref'd, inside the transaction that writes its `lane-exit:` (at most once per finalization, however often a busy write retries), with the ended lane's binding (`AGENT_SYSTEM_ROLE`, `AGENT_SYSTEM_WORKLOAD_ID`, `AGENT_SYSTEM_LANE_ID`) dropped from its environment (`starterEnv`) and its cwd in `~/.agent-system-2/lanes/`; the line `spawned <pid> by <laneId>` lands in `~/.agent-system-2/lanes/drain.log` before that transaction commits. The drain's first act is an empty ledger write, which waits for the runner's commit, so it reads the freed slot. It then works sequentially: it reads the open workloads oldest first, takes the first one it has not yet tried whose predicate (`verdictOf` over `launchRows`) says launch, runs the starter `launch <wl> --requested-by lane-runner` and waits for its own exit, with no timeout and no kill (a kill could land after the starter's reservation commits and before its runner spawns, leaving its pre-claim holding the slot until the 3-minute lease lapses, with no runner to release it and no drain to follow, so the queue behind it waits for an orchestrator tick; the starter's own exception path, `failAfterReserve`, is what releases a failed reservation), logs `attempt <pid> <wl> exit <code>: <line>`, and reads again; it stops at exit 6 (`cap`) or when nothing launchable is left untried, trying each workload at most once, and logs `start`, `end` and `failed` lines around it. Every launch it makes consumes its cause through `reserveLane` like any other, so it relaunches nothing the tick would not (decision 7), and every lane it starts drains again at its own exit. The drain covers the runner's exit only: a by-hand lane (`as2 lane <wl>`) ending, `lane.ts stop` acting with no runner alive, and a runner killed before its finalization free a slot that the tick still catches. The tick's `poll` now runs inside a try/catch, so a throw in it is queued as `tick: the poll failed: <error>` and the catch-up runs that tick anyway. The catch-up's own push of its notices goes through the same `sendMessage` and can throw once the session's wake has settled; the tick catches that rejection and writes `surface: the tick's catch-up failed: <error>` to stderr, never a second send (it would throw again) and never an unhandled rejection, and the batch stays queued for the next poll's resend.

Stop path (`as2 lane stop <wl>`, a mode flip, or Jo's "stop"): the surface (or `lane.ts stop` through the module) writes the request `lane-stop: <laneId> requested by <who> reason <r>`; the runner polls the ledger every 5 s and sees it (or receives SIGTERM/SIGINT), persists `lane-stop: <laneId> accepted <request entry id | signal>` before anything else, then sends `abort` (`modes/rpc/rpc-types.ts:33`), closes stdin, waits up to 30 s for exit, then SIGKILLs `omp` through its own child handle (`child.kill()`; no PID re-check, the child has not exited), and finishes as above with outcome `stop` and the real code and signal in `lane-exit:`. The accepted entry is what keeps the lane row's shutdown handler from writing `lane-died:` for the open or paused slices a stopped lane still has (decision 14); a `prompt_result` that arrives after the abort leaves the outcome `stop`.

## 5. Ledger changes

Under the recommendation (module level, schema stays at version 5, `ledger/schema.sql:622`, `PRAGMA user_version = 5`):

- `releaseWorkload(id, input: Stamp & { holder: string })`: the `UPDATE … WHERE id = ? AND holder = ?`; zero rows returns `{ released: false, holder }` instead of throwing. Callers migrated: the lane row's shutdown (`surface/extensions/lane.ts:144`, which also gains the `exitClass` check of decision 14 before its `lane-died:` enqueue at `:141-142`), `recordLapsedLease` and the surface's takeover path, the by-hand script's pattern.
- `reserveLane(workloadId, { by, cap, leaseMs, interactive? })` as in decision 8 — one `write()` that reads the workload row, its entries, and its questions with their resolving instructions and slices, runs `launchable` (or the interactive policy) on them, and returns any refusal before a write; otherwise the pre-claim stamped `by: "lane-starter"` and `launch: <laneId> cause <cause> requested-by <who>` land in the same transaction; the live-lane count query joins `workloads` on `mode = 'autonomous' AND status = 'open' AND holder GLOB 'lane-*' AND (holder_lease_until IS NULL OR holder_lease_until >= now)`; the ordinal is `1 + count(entries where kind = 'assumption' and body GLOB 'launch: *')` on the workload, read inside the same transaction.
- `parkLane(workloadId, { by: "lane-runner", laneId, session })`: one `write()` that reads the questions whose `created_by` is the lane id (`ledger/schema.sql:133`) and, when any is open or resolved by an unconsumed resolution, writes `lane-parked: <laneId> questions <qids> session <path>`; returns `{ parked: false }` or `{ parked: true, open: <n> }`.
- `handoffWorkload(id, { by, holder, to })`: one `write()` with two updates — the holder-checked release, then the claim for `to` with a null lease. Two statements because a direct `lane-… → jo` update under the lane's live lease is exactly what `workloads_holder_no_steal` refuses (`ledger/schema.sql:416-419`, `WHEN OLD.holder IS NOT NULL AND NEW.holder IS NOT NULL AND NEW.holder IS NOT OLD.holder AND (OLD.holder_lease_until IS NULL OR OLD.holder_lease_until >= …)`); the pair passes it, and no other writer sees the gap inside the transaction. Zero rows on the first update is the typed `not the holder`. Once Jo holds with a null lease, the lane's claim cannot win it back (`ledger/src/index.ts:459-460`, `holder IS NULL OR holder = ? OR (holder_lease_until IS NOT NULL AND …)`), and a null lease is never recorded as lapsed (`surface/src/signals.ts:64`, `!workload.holder_lease_until`).
- `holders(workloadId)`: every holder the workload ever had, oldest first, once each — the new side of each `holder a->b` the `workloads_log_update` provenance trigger records (`ledger/schema.sql`, the `'holder ' || coalesce(OLD.holder, '-') || '->' || …` detail). `launchRows` carries it as `ReserveRows.holders`, so `done-because:` from a lane that claimed by hand, with no `launch:` entry, is still a holder's receipt after its release (the `awaiting-close` row, § 6). A reader over existing rows; no schema change.
- New `assumption` entry prefixes, the **reserved control prefixes**, parsed by `surface/src/launch.ts` the way `signals.ts` parses `lane-died:`: `launch:`, `launch-failed:`, `launch-requested:`, `lane-started:`, `lane-ready:`, `lane-exit:`, `lane-parked:`, `lane-stop:`, `worktree:`, `branch:`, `plan:` (decision 15; writer `orchestrator-surface`), `done:` (decision 16; writer `orchestrator-surface`) and `done-because:` (decision 16; writer = the workload’s holder). Each has fixed writers, and every reader (the predicate, `reserveLane`, `parkLane`, the runner's stop poll, `exitClass`) accepts an entry only when its `created_by` is one of them and the body parses: `launch:` — `lane-starter`, inside `reserveLane` only; `launch-failed:`, `worktree:`, `branch:` — `lane-starter`; `launch-requested:` — `orchestrator-surface` only (`SURFACE_BY`, `surface/src/types.ts:31`); `lane-started:`, `lane-ready:`, `lane-parked:`, `lane-exit:` — `lane-runner`; a `lane-stop:` request — `orchestrator-surface` or `lane-starter` (`lane.ts stop`); a `lane-stop: … accepted` — `lane-runner`, or `lane-starter` when `lane.ts stop` acts with no runner alive. Text inside a body (`by jo`) is never authority; the stamp is. A lane's own writes carry its lane id (`surface/extensions/lane.ts:104`, `recordEntry({ by: s.laneId, …`), so no lane can supply a control entry a reader honours, and the lane tools refuse the prefixes outright (§ 4) so a note is refused rather than silently ignored. No new `kind` value (the `entries.kind` CHECK, `ledger/schema.sql:207`, is unchanged).
- New message body `lane-died: <laneId>: launch failed at <stage>: <reason>` and `lane-died: <laneId>: <outcome> (exit <code>)` from the runner — both match `LANE_DIED_BODY` (`surface/src/signals.ts:48`).

## 7. Open build questions

2. **Process start time source.** `ps -p <pid> -o lstart=` on macOS versus `proc_pidinfo`, behind one `startTime(pid)` helper in `lane.ts`: the runner calls it once to record `lane-started:`, and `lane.ts stop` is the only caller that compares it before a signal.
3. **First-prompt template.** The rendered brief (workload row, stakes, mode, `repo:`, decision-log context, "call `ledger_wake_read` first", the ledger tools by name) is a `surface/src/launch.ts` template; its exact wording is decided with the tier text. The design does not depend on it — stop is `abort` + stdin EOF, and SIGKILL is covered by the runner's release — but the fake-omp tests should not assume it either.
5. **`as2 lane` on Linux.** `lane.ts` is Bun, so portable; `ps` flags and `setsid` availability differ. macOS first (the ledger-backup agent has the same note, `install/manifest.tsv:118-120`).
6. **How a tool ends its own session.** `lane_release` and `lane_handoff` set the released flag, then end the session.
